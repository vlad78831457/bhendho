# Оплата промокодами: как это устроено

Решение — ADR-57, контракт для службы оплаты — `contracts/interfaces/promo_issuer.openapi.yaml`.

## Коротко

Деньги и приложение разделены. Приложение (ядро OFFGRID) не знает ни банка, ни кассы, ни страны — оно знает только промокоды. Промокод — это «чек на N GC», который выписала служба оплаты после того, как получила деньги.

```
покупатель ──₽──► служба оплаты ──► провайдер (ЮKassa, Т-Банк, Stripe…)
                  │  деньги пришли
                  ▼
                  выпускает промокод на N GC ──► ядро OFFGRID: хранит хэш кода
                  │
                  ├─ (а) отдаёт код покупателю (письмо, экран «спасибо») ──► пользователь вводит код
                  └─ (б) сама сообщает ядру «оплачено, зачислите user@mail» (вебхук)
                                                                   ▼
                                                      ядро один раз кладёт N GC на кошелёк
```

## Ответы на вопросы

**Кто создаёт промокод?** Служба оплаты — «эмитент». Это отдельная программа со своим токеном доступа к ядру. Их может быть несколько: своя касса в России, своя за границей, партнёр, который дарит коды своим клиентам. Ещё коды может создать оператор командой в консоли — для тестеров и подарков, без оплаты.

**Кто помечает, что он оплачен?** Никто в ядре. Промокод появляется только после оплаты: служба оплаты сначала получает подтверждение от своего провайдера (платёжный вебхук провайдера приходит к ней, а не к нам), и только потом выпускает код. Сам факт существования кода и есть «оплачено». Если деньги пришлось вернуть до того, как код погашен, служба отзывает код.

**Кто проверяет (валидирует)?** Ядро, в момент ввода кода:
- такой код есть и он выпущен этим эмитентом (для вебхука);
- не погашен и не отозван;
- не истёк срок;
- если код персональный — вводит тот, для кого он выпущен.

И ещё ядро ограничивает подбор: после 10 неверных кодов за 15 минут пользователь ждёт.

**Что внутри промокода?** Сам код — просто случайные 16 символов вида `K7PQ-M3XA-9FDE-TW2H` (буквы и цифры без похожих 0/O и 1/I, чтобы легко продиктовать). Угадать его нельзя — это 80 бит случайности. Всё остальное хранит ядро рядом с кодом:

| Поле | Зачем |
|---|---|
| сумма и валюта | сколько GC зачислить |
| эмитент | кто выпустил (в записи депозита: провайдер `promo:shop`) |
| номер заказа (`external_id`) | служба оплаты может безопасно повторить запрос — второй код не появится |
| email получателя (необязательно) | персональный код: погасит только этот человек |
| срок действия (необязательно) | после него код не принимается |
| статус | активен → погашен (кем, когда) или отозван |

Самого кода в базе нет — только его отпечаток (хэш). Даже с копией базы коды не украсть.

**Как устроены корзины?** Корзина не нужна. Пользователь покупает не товары, а пакет GC («500 GC за 500 ₽»), а GC уже тратятся на сказки: при запуске ядро резервирует цену (сказка — 150 GC), после генерации списывает по факту, остаток возвращает. Если понадобятся пакеты разного размера, скидки или акции — это витрина службы оплаты; ядру всё равно, как посчитан код, ему важна только сумма.

## Что видит пользователь

На экране сказки в шапке — кнопка «Промокод»: ввёл код → «Зачислено 500 GC» → баланс вырос. Если денег на сказку не хватает, экран так и говорит: «сказка резервирует 150 GC, доступно 30 GC — пополните баланс промокодом». Регистр и пробелы в коде не важны. Повторный ввод своего уже зачисленного кода ничего не ломает: «Этот промокод уже зачислен вам».

То же поле есть в кошельке на `/schema/`.

## Оператор: подарочные коды из консоли

```bash
cd ~/projects/taleweaver-app-vr-ab/ecosystem
docker compose exec core /core promo-codes --amount 500 --count 5              # 5 кодов по 500 GC
docker compose exec core /core promo-codes --amount 300 --days 30              # срок 30 дней
docker compose exec core /core promo-codes --amount 1000 --email tester@mail.ru # персональный
```

Коды печатаются один раз — сохраните их сразу. Выпускает их эмитент `operator` (создаётся сам).

## Служба оплаты: подключение

1. Токен эмитента. Либо в `.env` стека (`make init-env` создаёт `PROMO_ISSUER_TOKEN`, эмитент называется `shop`), либо командой `docker compose exec core /core promo-issuer --name shop` (печатает токен один раз; старый перестаёт работать).
2. Все запросы — с `Authorization: Bearer <токен>` на адрес фронта: `/issuer/v1/…`.
3. После оплаты — выпустить код, передав номер заказа:

   ```bash
   curl -s https://<домен>/issuer/v1/promo-codes -H "Authorization: Bearer $TOKEN" \
     -d '{"amount": "500", "external_id": "order-1042", "for_email": "buyer@mail.ru"}'
   # → {"code_id": "…", "code": "K7PQ-M3XA-9FDE-TW2H", "amount": "500.0000", "status": "active", …}
   ```

   Дальше — отдать код покупателю, либо сразу зачислить сам (вебхук):

   ```bash
   curl -s https://<домен>/issuer/v1/redeem -H "Authorization: Bearer $TOKEN" \
     -d '{"code": "K7PQ-M3XA-9FDE-TW2H", "user_email": "buyer@mail.ru"}'
   ```

4. Возврат денег до погашения — `POST /issuer/v1/promo-codes/<code_id>/revoke`. Статус — `GET /issuer/v1/promo-codes/<code_id>`.

Повторы безопасны: тот же `external_id` не выпустит второй код, повтор вебхука не зачислит дважды.

## Что пока не сделано

- **Сама служба оплаты** с настоящим провайдером (ЮKassa, Т-Банк, Stripe…) — отдельный проект; ядро и контракт к ней готовы.
- **Возврат денег после погашения** — это уже списание GC с кошелька, отдельная операция ядра (корректировка), её пока нет.
- **История промокодов в кабинете** — войдёт в кабинет (`task/ak-cabinet`); сейчас пополнения видны в журнале кошелька на `/schema/`.
