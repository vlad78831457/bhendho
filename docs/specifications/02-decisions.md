# 02 · Журнал архитектурных решений (ADR)

> История решений перенесена из `r-aaa-core-a` / `taleweaver-app-vr-ab` 2026-10-03 как есть. ADR о модулях (сказки, закупки, тьюторы, алгоритмы) и фронте относятся к проектам этих модулей и сохранены для истории; новые решения ядра продолжают нумерацию с ADR-61.

> Формат каждой записи: контекст → решение → почему → последствия (включая неприятные).
> Новые решения дописываются вниз; старые не переписываем — помечаем статус «заменено ADR-XX».

## ADR-01 · Исходный концепт принят за основу

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** есть концепт-документ «Асинхронная Offline-First PWA экосистема с биллингом и AI-агентами»: PostgreSQL 16, Supabase (Auth/Realtime/Storage), Kong, воркеры-плагины, JSONB-формы, Transactional Outbox, внутренняя валюта, Cloud.ru Evolution AI.
- **Решение:** за основу берётся вся архитектурная механика концепта (outbox, JSONB, SKIP LOCKED, прогресс мимо БД). Целевые цифры («10 000 пользователей», сроки в 3 дня) — не считаются обязательными ограничениями.
- **Последствия:** архитектура не переписывается с нуля; правки вносятся этим журналом и спекой.

## ADR-02 · Один репозиторий (монорепа)

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** фронт, инфраструктура и воркеры можно разложить по разным репозиториям.
- **Решение:** всё в одном репозитории (`docs/`, `src/`, инфраструктура и воркеры появятся здесь же).
- **Почему:** команда ~1–10 человек, общие контракты (JSONB-схемы, события сокета), нет двойного CI/деплоя.
- **Последствия:** при выделении мобильного клиента или отдельной команды воркеров — вернуться и пересмотреть.

## ADR-03 · Supabase вместо собственного серверного кода

- **Дата:** 2026-06 · **Статус:** заменено ADR-43 (ядро — Go, Supabase не используется); принцип «деньги только транзакциями Postgres» сохранён
- **Контекст:** нужны регистрация, realtime, файлы, база. Писать свой Express/FastAPI-сервер или взять платформу?
- **Решение:** Supabase (GoTrue + Realtime + Storage + PostgreSQL). Бизнес-логика денег — в RPC-функциях Postgres, доступ клиентов — через RLS-политики.
- **Почему:** «регистрация и пополнение баланса» — это ровно то, что Supabase даёт из коробки; свой сервер на старте только добавляет код без новой ценности.
- **Последствия:** self-hosted compose Supabase хрупок — брать официальный compose и урезать, не писать свой. Альтернатива на время прототипа — Supabase Cloud.

## ADR-04 · Прототип в этом репозитории = живая спецификация

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** текстовое ТЗ быстро разошлось бы с реализацией; поведение системы проще показать, чем описать.
- **Решение:** интерактивный прототип (панель управления с Wi-Fi-тумблером, JSONB-конструктором, outbox и биллингом) остаётся в репозитории и служит эталоном механики; в будущем переиспользуется как админ-панель.
- **Последствия:** при расхождении кода M0+ с прототипом — сверяться и править оба.

## ADR-05 · Transactional Outbox для доставки событий

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** нужно, чтобы результат задачи или отказ не потерялись при обрыве сети клиента.
- **Решение:** событие пишется в `outbox_queue` в той же транзакции, что и изменение задачи; отдельный демон доставляет его в Realtime и повторяет при сбоях (`retry_count`).
- **Почему:** гарантия «at-least-once» без распределённых транзакций.
- **Последствия:** события могут прийти дважды — клиент обязан быть идемпотентным.

## ADR-06 · Деньги только через RPC, журнал транзакций append-only

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** списание за задачу — самая опасная операция системы; клиент никогда не должен иметь прямого доступа к балансу.
- **Решение:** баланс меняется исключительно RPC-функциями Postgres (`charge_task`, `refund_task`, `deposit`), каждая операция оставляет запись в `transactions` (INSERT-only, без UPDATE/DELETE). Списание, создание задачи и outbox — одна транзакция.
- **Последствия:** отладка денег сводится к чтению журнала; требуется idempotency_key для защиты от двойных списаний. Набор RPC уточнён ADR-29: `reserve_task` при создании, расчёт системным бухгалтером при фиксации результата.

## ADR-07 · Динамические формы в JSONB

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** формы задач различаются набором полей; классический подход — таблица полей + миграции при каждой новой форме.
- **Решение:** схема формы (поля, типы, валидация, цена) хранится в JSONB; интерфейс рендерит форму по схеме; `payload` задачи — тоже JSONB.
- **Почему:** добавление формы — это вставка строки, а не релиз; воркеру уходит самодостаточный payload.
- **Последствия:** нужна строгая валидация схемы на бэкенде (JSON Schema) — иначе мусорные формы.

## ADR-08 · SKIP LOCKED для очереди воркеров

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** несколько воркеров-плагинов одновременно забирают задачи из одной очереди.
- **Решение:** `SELECT … FOR UPDATE SKIP LOCKED` с переводом статуса в `processing` атомарным UPDATE; воркер, упавший в середине, отпускается по таймауту (задача возвращается в `pending`); таймаут и лимит попыток уточнены ADR-30 — 3 × оценка прораба, числа в конфиге.
- **Почему:** без внешних очередей (Redis/RabbitMQ) на этом этапе; Postgres справляется.

## ADR-09 · Стек фронтенда: Next.js App Router + PWA

- **Дата:** 2026-06 · **Статус:** заменено ADR-54 (стек: React + Vite SPA вместо Next.js; IndexedDB и service worker — в силе)
- **Контекст:** PWA с офлайн-режимом, динамические формы, состояние переживает перезагрузку.
- **Решение:** Next.js (App Router) + React + TypeScript + Tailwind; локальное состояние — IndexedDB; service worker кэширует оболочку.
- **Последствия:** офлайн-синхронизация требует идемпотентных RPC (см. ADR-06).

## ADR-10 · Бланк-конверт — единый контракт документов и задач

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** разбор учебного проекта (`musor/combined_project.py`, School 21) показал работоспособность паттерна «бланк»: единый конверт `system / meta_ui / values / commands / report` ходит через все слои — интерфейсы только отображают и читают правила из самого документа, контроллер маршрутизирует бланки по плагинам, реестр «статус × команда → обработчик» описывает жизненный цикл. Вердикт по разбору: для учебного проекта — сильно выше среднего; идея бланка — не учебный трюк, а рабочий паттерн, совпадающий с тем, что в OFFGRID уже независимо выбрано как JSONB-формы (ADR-07).
- **Решение:** в OFFGRID бланк-конверт становится единой формой для всех документов и задач. Каждый документ (форма, задача, результат, файл-манифест) — самодостаточный JSONB-конверт: `system` (тип, статус, адресат-плагин), `meta_ui` (как показать: поля, правила, маски), `values` (данные), `commands` (доступные действия со статусами), `report` (результат последней обработки). Один конверт — одна валидация, один роутер, одна матрица жизненного цикла. Инфраструктурные слова из прототипа: SourcePlugin → Supabase, реестр плагинов → реестр AI-агентов, единая точка `process()` → место списания/возврата денег (ADR-06).
- **Почему:** интерфейс перестаёт знать домен — он рендерит `meta_ui` и отправляет `commands`; новый тип задачи — это запись в реестре, а не релиз; прогресс и результат едут в том же конверте, что усиливает ADR-05.
- **Правила, вынесенные из ошибок референса:** (1) бланк иммутабелен между шагами — обработчик получает копию и возвращает новый конверт, мутация на месте и `clear()` запрещены; (2) один механизм ошибок — домен бросает исключение, на границе оно превращается в `report`, никакого `print` и трёх смешанных стилей; (3) все статусы сведены в один справочник (`system.status` + матрица команд), интерфейсам запрещено придумывать свои; (4) мёртвый код и черновики в комментариях не живут в репозитории.
- **Последствия:** нужна строгая JSON Schema конверта на бэкенде (см. ADR-07) — иначе мусорные конверты; вложенные бланки (бланк внутри бланка) разрешить только через ссылки, не копии; роутер и матрица статусов становятся ядром, их тесты обязательны.

## ADR-11 · Без стадии MVP: сразу рабочая версия, нарезка циклами

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** внешняя работа, под которую закладывался MVP, не состоялась («не взяли в работу») — исчезли чужой дедлайн и требование «быстрый урезанный демо-срез». Продукт делается для себя, сразу в рабочем качестве.
- **Решение:** стадия MVP отменяется. Разработка — циклами: каждый цикл завершается работающим вертикальным срезом всей цепочки (интерфейс → БД/RPC → воркер → realtime → результат), а не отдельным слоем. Приоритеты в спеке переосмыслены: M — ядро без которого смысла нет, S — нужно рабочей версии, C — после первой рабочей версии. То, что раньше откладывалось «на после MVP» (реальные платежи), теперь в горизонте рабочей версии, но каждый такой шаг — отдельный ADR.
- **Почему:** циклы сохраняют главный выигрыш MVP — рано работающую систему — без искусственного урезания объёма и качества; отсутствие внешнего заказчика снимает давление «показать хоть что-то за срок».
- **Последствия:** первый цикл крупнее бывшего MVP — главная опасность «сделаем всё и сразу»; правило против: цикл закрывается только когда его срез реально работает end-to-end; спека и этот журнал остаются живыми — состав цикла переоценивается в его начале.

## ADR-12 · Шаблоны — вниз, заполненные бланки — вверх; фронт не утверждает цену

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** фронтов у системы будет много (PWA, мобильный, админка, скрипты). Разбор прототипа показал дыру: `submitTask(schema, values)` отправляет на сервер **всю схему формы, включая цену** — фронт фактически сам утверждает стоимость. В демо это безвредно, в рабочей версии с разными фронтами — прямой способ подменить цену или поля.
- **Решение:** направления потоков фиксируются (спека, 5.7): вниз уходят **шаблоны бланков** (каталог и `meta_ui`, read-only), вверх приходят **заполненные бланки без схемы и цены** — только `form_id` + `values` + `idempotency_key`. Сервер сам достаёт шаблон, назначает цену, валидирует. Контракты фронт-агностичны: новый фронт собирается из тех же потоков, без правок API.
- **Почему:** цена и валидация существуют только в одном месте — на сервере; любой фронт (включая будущие) не может сломать биллинг; уменьшается объём вверхнего трафика.
- **Последствия:** прототипу при переходе на реальный бэк (M0+) потребуется изменить `submitTask(schema, values)` → `submitTask(form_id, values)`; реестр realtime-событий становится контрактом — изменения payload версионировать.

## ADR-13 · Два принципиальных типа бланков: факт-бланки и задача-бланки

- **Дата:** 2026-06 · **Статус:** принято с уточнениями
- **Контекст:** автор предлагает разделить бланки на два принципиальных вида. (1) **Факт-бланки** — записи только из фактов, пишутся в БД: описания однородных объектов (карточки), могут содержать файлы и ссылки `id_db` на другие факты. (2) **Задача-бланки** — задания для AI или иных исполнителей; в них — факты или ссылки `id_db` на факты, а заполняет их **промежуточная среда**: читает факты из БД по ссылкам, собирает самодостаточный бланк и передаёт исполнению.
- **Решение:** в модели данных появляется два типа бланков с общим конвертом (ADR-10):
  - **факт-бланк** (`kind=fact`): хранится в таблице `facts` (JSONB-значения + манифесты файлов), на него ссылаются по `id_db`; жизненный цикл — черновик → опубликован → (архив); money-операций нет; Realtime-событие `fact.changed`;
  - **задача-бланк** (`kind=task`): хранится в `system_tasks`; в `values` — скаляры и **ссылки** `fact_ref → id_db`; создаётся через RPC (ADR-06) с получением цены из шаблона (ADR-12);
  - **промежуточная среда (материализатор)**: серверная функция/воркер-этап перед постановкой в очередь разворачивает ссылки в значения (или передаёт воркеру подписанные URL). Воркер получает самодостаточный бланк и не ходит в БД за фактами.
- **Почему:** факты переиспользуются многими задачами без копирования; воркер изолирован от БД (NFR-3); история задачи фиксирует, какие данные реально видели воркеры; факт-бланки дают системе содержимое ещё до появления биллинга и AI.
- **Правила (уточнения к исходной идее):** (1) в бланке задачи на хранении — только ссылки; материализация — при постановке в очередь, результат материализации прикладывается к задаче (какая версия факта ушла воркеру); (2) факт иммутабелен по-версионно: правки создают новую версию, `id_db` указывает на последнюю; (3) удаление факта запрещено, пока на него есть ссылка из незавершённой задачи.
- **Последствия:** нужна таблица `facts` + JSON Schema обоих конвертов в цикле M0/M1; материализатор — новый обязательный этап между RPC и SKIP LOCKED; версия факта в задаче — ещё один аргумент за версионирование шаблонов (инбокс).

## ADR-14 · Materialized-снимок: воркеру уходит снимок, не ссылки; завершённая задача неизменяема

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** ADR-13 отправляет воркеру самодостаточный бланк, но не фиксирует его состав: что именно ушло воркеру, если факт правнут или файл удалён между созданием задачи и её забором? Подписанные URL в бланке протухают.
- **Решение:** при постановке в очередь материализатор собирает и записывает в задачу поле `materialized` — снимок: тела фактов тех версий, что ушли воркеру, и пути файлов (`bucket/uuid`, не URL). Подписанные URL генерируются в момент забора задачи (TTL на время выполнения). Завершённая задача неизменяема: снимок и результат хранятся как есть; «переделать» задачу нельзя — только пересоздать новым бланком.
- **Почему:** снимок отвечает на вопрос «какие данные реально видели воркеры» — это и отладка, и повторяемость, и честная история; пути вместо URL делают снимок вечным.
- **Последствия:** `materialized` может быть объёмным — это осознанная цена; удаление файла/факта до материализации ловится на постановке в очередь (см. матрицу примитивов, FR-FORM-9).

## ADR-15 · Статусы фактов и ссылка fact_ref: голый id, задача ставится только на published

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** жизненный цикл факта из ADR-13 («черновик → опубликован → архив») нуждался в точных статусах и формате ссылки `fact_ref` из задачи-бланка: голый id или `{id, version}`?
- **Решение:**
  1. Статусы версии факта: `draft / published / archived / deleted (tombstone)`. Задачи ставятся только на `published`; `id_db` указывает на последнюю опубликованную версию.
  2. `fact_ref` в бланке задачи — **голый id** (дисциплина ссылок ADR-13: ссылка не копирует данные); версию для снимка выбирает материализатор в момент постановки в очередь (последнюю published).
  3. Задача-бланк — не факт: `fact_ref` указывает только на `facts`; источником новой задачи может быть только факт — в том числе факт-результат прежней задачи.
  4. Происхождение факта: `origin = user / task:<id>`; результат задачи оформляется факт-бланком `origin=task`, файлы-результаты — в его манифестах.
  5. Версия факта от воркера приходит в `draft`; публикация/скрытие/удаление — решение пользователя; «черновики от воркера» — часть интерфейса фактов.
- **Почему:** голый id не дублирует данные и не устаревает; «только published» отделяет черновики пользователя от того, что можно отправлять в исполнение.
- **Последствия:** tombstone удаляет ссылками не блокируется — снимки хранят тела (ADR-14), живость файлов — по реестру (ADR-16); потеря/непубликация факта после постановки в очередь — отказ материализатора с полным возвратом (`FACT_MISSING`).

## ADR-16 · Реестр файлов — единое место правды о «живости»; файл — тип поля формы

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** манифесты файлов лежат в фактах и бланках (снимки), а файл в Storage можно удалить. Где истина: жив файл или нет? И чем файл является в схеме формы — украшением или типом поля?
- **Решение:**
  1. Единственное место правды о «живости» файла — реестр `files` (статусы `active / deleted (tombstone)`); объект Storage иммутабелен (имя = uuid, перезапись запрещена), «удаление» — tombstone в реестре.
  2. Файл — тип поля формы/факт-формы наравне со скалярами (см. матрицу примитивов FR-FORM-9); реестр хранит родителя (факт/задача) и `field_code` поля — по ним файл находит своего владельца.
  3. Манифест в бланке/факте — снимок (uuid, имя, размер, mime) и никогда не обновляется: история читаема даже после tombstone.
  4. «Файл живёт меньше факта»: сжатие версии факта переводит её файлы в tombstone (ADR-17).
- **Почему:** проверка живости сводится к одному запросу в реестр; снимки остаются честной историей, а не рассинхронизированными копиями.
- **Последствия:** потеря обязательного файла ловится до воркера (`FILE_MISSING` + возврат), необязательного — маркер `LOST_REF` в снимке; квоты и происхождение файлов — в реестре.

## ADR-17 · Сжатие фактов — только команда пользователя; заглушки вместо старых версий

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** версионные факты (ADR-15) неограниченно растут: каждая правка — новая версия, каждая версия может нести файлы. Нужна политика старения — но автоматическое удаление данных пользователя недопустимо.
- **Решение:**
  1. Сжатие — всегда команда пользователя, автосжатия нет.
  2. Прореживание истории версий по двум параметрам — количество и возраст; параметры задаёт настройка факт-формы. Последняя версия остаётся целиком всегда.
  3. Сжатая версия превращается в заглушку: id, номер версии, дата, origin, описание. Тело и файлы уходят; файлы сжатых версий → tombstone в реестре (ADR-16).
  4. Журнал транзакций сжатие не касается никогда.
  5. Перед сжатием интерфейс предлагает скачать результаты (и файлы версий) на устройство.
- **Почему:** пользователь владеет решением о потере данных, система лишь делает дешёвым хранение истории; заглушки сохраняют целостность ссылок и хронологии.
- **Последствия:** лишние поля в теле факта стираются при сжатии — они не ошибка валидации, а временные данные (ADR-21); квота объёма пользователя считается по реестру файлов.

## ADR-18 · Воркеры ходят только через единый шлюз; идентичность — service-аккаунт

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** ADR-13 изолирует воркер от БД, но не отвечает: кто выдаёт задачу, кто принимает результат и прогресс, как отличить одного воркера от другого в `locked_by` и в RLS-матрице (NFR-2)?
- **Решение:** единственное окно обмена для любого воркера — **шлюз материализатора**: claim (SKIP LOCKED) → выдача materialized-бланка → приём прогресса → приём результата/ошибки. У каждого воркера своя идентичность — service-аккаунт; он и попадает в `locked_by`. В БД пишет только шлюз; RLS-политик для воркеров нет — есть политика шлюза.
- **Почему:** один вход = один контракт и одна точка проверки прав; новый плагин — регистрация service-аккаунта, без изменений БД и бэкенда (NFR-3); прогресс и результат нельзя подделать со стороны.
- **Последствия:** шлюз становится обязательным элементом цикла M2; heartbeat/ретраи соединения воркера со шлюзом — забота шлюза, не схемы БД. Сторона исполнения на стыке получает имя «прораб» — приём бланка с оценкой времени, попытки — ADR-30.

## ADR-19 · Версионирование шаблонов: append-only, задача фиксирует schema_version

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** правка формы не должна менять уже созданные задачи (у них в бланке зафиксированы цена и поля на момент создания). Как при этомкатать воркеры на новые версии?
- **Решение:**
  1. Правка шаблона = новая версия, append-only; старые версии не переписываются.
  2. Задача фиксирует `schema_version` — версию, по которой сервер валидировал `values` и взял цену; валидация и цена всегда по зафиксированной версии.
  3. «Новая группа воркеров» = маршрутизация claim по паре `(target_service, schema_version)`; старая группа дочитывает свою очередь и вымывается естественно.
  4. Ни deprecated-механик, ни миграций — и всё на этом.
- **Почему:** цена и валидация становятся воспроизводимыми: по бланку задачи можно точно восстановить, по какому контракту она исполнялась.
- **Последствия:** индекс очереди — `(target_service, schema_version, status, created_at)`; фронт получает версию шаблона вместе с шаблоном. «Цена» шаблона в механике ADR-29 — потолок-резерв.

## ADR-20 · Идемпотентность: ключ на задаче; шлюз — транзакционная граница, а не конец брокера

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** офлайн-клиент (ADR-09) и ретраи шлюза дают повторы одной и той же отправки. Где ставить уникальность и что возвращать при повторе? И не становится ли шлюз «концом брокера сообщений»?
- **Решение:**
  1. Уникальный `idempotency_key` — на строке `system_tasks`, не на `transactions`. Повтор с тем же ключом возвращает существующую задачу (её текущее состояние); TTL ключу не нужен. `transactions` остаётся append-only без ограничений.
  2. Создание задачи, списание и outbox-событие — одна транзакция (ADR-06/12).
  3. Фиксация решения воркера: `UPDATE … WHERE status='processing' AND locked_by=этот воркер`; 0 строк — шлюз возвращает текущее состояние строки, воркер выбрасывает свой результат. Дедуп по состоянию строки, не по ключу.
  4. Шлюз — **не** конец брокера сообщений: брокера нет, очередь одна (Postgres). Шлюз — транзакционная граница; at-least-once между воркером и шлюзом даёт связка «повтор commit + дедуп по состоянию строки»; доставкой событий клиенту занимается outbox-демон (ADR-05).
- **Почему:** ключ на задаче защищает ровно то, что нужно — от двойного создания задачи и двойного списания; дедуп по состоянию строки переживает любые повторы без отдельного журнала «принятых» результатов.
- **Последствия:** конверт отправки бланка обязан нести `idempotency_key` (FR-IF-2); клиент генерирует ключ один на логическую отправку и не меняет его при ретраях.

## ADR-21 · Реестр типов фактов не строится: kind — сами факт-формы

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** напрашивался отдельный реестр типов фактов (зеркало ADR-07 для фактов): справочник kind, схемы по kind, проверка совместимости `fact_ref`-полей.
- **Решение:** отдельный реестр не строится — **kind = сами факт-формы** (шаблоны факт-бланков). `fact_ref`-поле объявляет ожидаемый kind прямо в схеме задачи. Совместимость проверяют те, кто читает ссылки: валидатор при создании и материализатор в очереди. «Чего нет — того нет»: несуществующий kind — это код отказа в report. Лишние поля в теле факта — не ошибка: лежат до сжатия, тело стирается при сжатии (ADR-17).
- **Почему:** факт-форма уже есть схема и источник правды о kind; дублирующий реестр был бы вторым местом, которое надо синхронизировать.
- **Последствия:** конструктор форм показывает в выборе `fact_ref` только опубликованные факт-формы; kind в схеме поля — голый id факт-формы (та же дисциплина ссылок, что ADR-15); инбокс-пункт «реестр типов фактов» закрыт.

## ADR-22 · Матрица «статус × команда»: пять статусов задач, cancel из очереди, retry — пересоздание, refund_pending не нужен

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** ADR-10 назвал матрицу ядром жизненного цикла с обязательными тестами, но самой матрицы не было. Открытым было: cancel/retry из каких статусов; нужны ли статусы `cancelled` / `refund_pending`; как вписывается команда «сжать» (ADR-17).
- **Решение:**
  1. Справочник статусов задач — пять: `pending, processing, completed, failed, cancelled`. `refund_pending` не вводится: возврат денег атомарен смене статуса в одной транзакции (шлюз «помечает задачу и транзакцию» — ADR-20 п.2), промежуточное бухгалтерское состояние не нужно — деньги не «висят» между статусами.
  2. Пользовательские команды: `cancel` — только из `pending` (полный возврат в той же транзакции; из `processing` запрещена — гонка с фиксацией воркера, исход решат `completed`/`failed`). `retry` — только из `failed` по вине исполнения; семантика — пересоздание (ADR-14): новая задача с тем же materialized-снимком и повторным списанием (деньги по `failed` уже возвращены — журнал читается честно: charge → refund → charge). `failed` по данным (`FACT_MISSING`/`FILE_MISSING`) команды retry не получает — только пересоздание бланка человеком. У `completed` команд нет — «повторить» на фронте = новый бланк, не команда.
  3. Системные переходы (не команды): `pending→processing` — claim шлюза (SKIP LOCKED, ADR-18); `processing→pending` — лок истёк без результата (ADR-08), счётчик попыток +1; `processing→completed` — commit воркера (ADR-20); `processing→failed` — воркер сообщил об ошибке либо лимит попыток исчерпан → полный возврат; `pending→failed` — отказ материализатора до очереди (ADR-14) → полный возврат.
  4. Факты сведены в ту же таблицу-справочник из уже принятого (ADR-15/16/17); дополнено одно следствие: возврат из `archived` в `published` разрешён (человек передумал) и сдвигает `id_db` на возвращённую версию — симметрично обычной публикации.
  5. Правило 3 ADR-10 усилено: интерфейсам запрещено придумывать статусы; отказ команды — report (его формат остаётся в инбоксе).
- **Почему:** пять статусов покрывают весь цикл без бухгалтерских прослоек — возврат атомарен статусу; retry-как-пересоздание держит append-only философию (ADR-13/14) и чистый журнал денег.
- **Последствия:** `cancelled` — статус каркаса, реализуется вместе с FR-BILL-7 (поздний цикл); числа (таймаут лока, лимит попыток) — решены ADR-30: ожидание — 3 × оценка прораба, лимит 5, поля лока — locked_until и attempts; каждая клетка матрицы получает тест «команда из недопустимого статуса → отказ в report, ни деньги, ни статус не тронуты» (критерий приёмки 5.9); инбокс-пункт «матрица статус × команда» закрыт. Механика денег уточнена ADR-29: при создании — резерв (списание — в момент завершения по факту), «полный возврат» = снятие резерва; до успеха деньги не покидают кошелёк.

## ADR-23 · Realtime-доставка: seq/dedup, heartbeat с backoff, кнопка «проверить сеть», тайминги в конфиге

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** at-least-once (ADR-08) означает возможные дубли, а порядок «snapshot → догоняющие события» (FR-IF-5) канал не гарантирует — без защиты баланс и статусы на экране будут дёргаться. Соединение может умирать тихо: оба конца молчат и не знают, что связи нет. Дополнительно от пользователя: применённые события сразу писать в локальную базу (он может быть на другой странице), тайминги держать в конфиге, при долгом отсутствии сети не бомбить сервер пингами, дать кнопку ручной проверки сети.
- **Решение:**
  1. **seq/dedup.** Каждое событие несёт сквозной порядковый номер `seq` (счётчик на пользователя, выдаёт outbox-демон при доставке). Клиент хранит последний применённый номер: события с `seq ≤` применённого молча отбрасываются. `system.snapshot` несёт `seq` момента выдачи — догоняющие события с большим номером применяются, с меньшим — игнорируются; гонка «снапшот против outbox» закрыта, дубли безвредны: «хотя бы один раз» на канале превращается в «эффект ровно один раз» на клиенте. В эскизе модели — колонка `seq` в `outbox_queue` (M0).
  2. **Heartbeat.** Пинг каждые N секунд (базово 15): три пропуска подряд — соединение считается мёртвым, переподключение инициирует клиент (порог по умолчанию 45 с тишины). Потеря `task.progress` за время тишины безопасна — прогресс эфемерен (5.7).
  3. **Backoff.** Пока сеть не вернулась, интервалы переподключения растут (удвоение) до установленного потолка (базово 60 с) — сервер не получает шквал пингов, когда канал лежит на стороне пользователя. После успеха — snapshot + догоняющие.
  4. **Кнопка «проверить сеть».** Ручной запуск проверки: немедленный ping вне таймера backoff; успех → переподключение, snapshot, догоняющие (FR-OFF-4).
  5. **Событие сразу в локальную базу.** Применённое (после dedup) событие клиент сразу пишет в локальную базу пользователя (IndexedDB) — пользователь может быть на другой странице и занят другим; экраны читают состояние из локальной базы, а не напрямую из сокета. Принцип зафиксирован; механика слоя — при разработке фронт-архитектуры.
  6. **Числа — в конфиге.** Интервал пинга, порог тишины, потолок backoff — параметры конфигурации приложения, не константы в коде.
- **Почему:** dedup закрывает и дубли, и гонку со snapshot; heartbeat ловит тихо умершие соединения; backoff щадит сервер, кнопка — даёт пользователю контроль; конфиг позволяет менять тайминги без перевыпуска кода.
- **Последствия:** клиентский слой обязан применять события в порядке `seq`; счётчик и колонка — в M0 вместе с outbox; оба realtime-пункта инбокса закрыты.

## ADR-24 · Report и trace: один вердикт — три взгляда; трасса — стек стыков, маршрут — кольцо

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** формат report — последний открытый контракт из инбокса: коды ошибок, где исключение домена превращается в отчёт, код отказа команды из матрицы (ADR-22). Предложение автора: отчёт существует в трёх видах — пользователю, админу, системе; report — системный бланк, идущий рядом с задачей и собирающий единый список (лог и трассировку); на стыке шлюз↔воркер действует правило «дал бланк — получи обратно»; виды трасс — стек, очередь, кольцо (авторское), дерево (автор засомневался); отчёты админу и системе хранятся в базе с привязкой к id задачи и протухают через 14 дней; пользователю — короткое сообщение: что сделано / почему плохо / где сломалось / когда потерялось. Лестница акторов: «пользователь ноль» — центральная система, дальше воркеры, потом админы; когда всё хорошо — хорошо, когда плохо — кто-то должен лечить; центральная система защищает себя всегда.
- **Решение:**
  1. **«Отчёт» разделяется на два артефакта.** **Вердикт (report)** — приговор об обработке бланка, блок конверта из ADR-10: результат либо код отказа из единого реестра. **Трасса (trace)** — протокол пути задачи по этапам: append-only записи (этап, актор, время, код, детали). Разделение навязано двумя правилами сразу: завершённая задача неизменяема (ADR-14) — вечный вердикт живёт в конверте; трассе назначен TTL — протухать может только то, что хранится отдельно от неизменяемого.
  2. **Три взгляда одного факта.** Системе — код: он же вход матрицы (ADR-22), класс отказа определяет retry, атрибут «кто лечит» — маршрутизацию починки. Админу — трасса целиком: этапы, service-аккаунты (ADR-18), времена, детали — материал для ответа «кто должен лечить». Пользователю — короткое сообщение, собираемое системой из шаблона; формула автора зафиксирована как четыре слота: **что** сделано / **почему** нет / **где** сломалось / **когда** потерялось. Свободный текст воркера к пользователю не проходит — только шаблоны системы; текст воркера уходит в админский взгляд.
  3. **Реестр кодов — один (5.10).** Код несёт: этап, «кто лечит» (система сама / админ / пользователь), класс (данные / исполнение / transient) и шаблон сообщения. Класс определяет retry по матрице (ADR-22): вина данных — retry нет, вина исполнения — retry есть (пересоздание из снимка, ADR-14). Правило пополнения: **код без строки реестра не существует** — нет кода без этапа, «лечащего» и шаблона. Отказ команды из матрицы — код `COMMAND_REFUSED` с деталью (какая команда и почему нельзя).
  4. **Топологии.** Правило **стека** — на каждом стыке: кто получил бланк, обязан вернуть его с отчётом тому, кто дал (клиент↔RPC, RPC↔материализатор, шлюз↔воркер). Незакрытого стыка не бывает: молчание воркера закрывает таймаут лока (ADR-08) и само становится отчётом (`WORKER_TIMEOUT`, попытка +1) — «нет ответа» тоже ответ. Правило **кольца** — на маршруте в целом: бланк всегда возвращается в начальную точку, к пользователю, хотя бы отказом — это гарантируют outbox (ADR-05) и seq/dedup (ADR-23). **Очередь** — не топология, а комната ожидания: вход и выход из неё — обычные записи трассы. **Дерево** в потоке бланков не вводится: ветвится не исполнение, а данные (факты и ссылки, ADR-13/15); веер «одна задача → несколько исполнений» ломает биллинг и неизменяемость — если однажды понадобится, отдельный ADR.
  5. **Защита системы.** Отчёт воркера шлюз принимает только по JSON Schema: мусор или неизвестный код → `REPORT_INVALID`, результат не фиксируется (дедуп по состоянию строки, ADR-20), задача → failed по вине исполнения. Вердикт после фиксации иммутабелен: спорный отчёт не «правится» — лечится новой задачей (retry/пересоздание). Команды пользователей проверяет матрица (FR-IF-7). Лестница автора («ноль» — центральная система) читается как порядок лечения: сначала система лечит себя сама (ретраи, возвраты, дедуп), непоправимое в воркерах — админ, данные и деньги — пользователь; вниз по лестнице система никому не верит без проверки.
  6. **Хранение и TTL.** Трасса — таблица `task_trace` рядом с задачей, привязка по `task_id`, append-only, TTL **14 дней** (параметр в конфиге, как тайминги ADR-23), чистит фоновое задание. Вердикт и пользовательское сообщение — часть конверта задачи, не протухают.
- **Почему:** три взгляда — проекции одного факта, а не три отчёта: единый реестр не даёт разъехаться «что видит админ» и «что сказано пользователю»; «кто лечит» в коде превращает отказ в назначенную работу, а не в сообщение об ошибке; стек + кольцо описывают любой маршрут без новых сущностей; TTL только на трассе снимает конфликт с неизменяемостью задачи.
- **Последствия:** таблица `task_trace` — в эскизе модели (раздел 7), появляется вместе с задачами (M0/M2); JSON Schema отчёта воркера — часть контракта шлюза (M2); отказы в тестах матрицы — только кодами из реестра; экран админа группирует отказы по «кто лечит» (FR-ADM-1/3); новый раздел 5.10; инбокс-пункт «формат report» закрыт.

## ADR-25 · OAuth-провайдеры — конфигурация развёртывания, а не выбор архитектуры; стартуем с Google

- **Дата:** 2026-06 · **Статус:** принято; п. 3 уточнён ADR-32 — базовый вход email/пароль, OAuth — следующий уровень
- **Контекст:** открытый вопрос «какой первый OAuth-провайдер». Предложение автора: провайдера определяет фактическое приложение и ареал основных клиентов — платный продукт может тянуть OAuth Сбера, RU-зона — VK, Android-телефон — Google; принципиально другое — **адаптивность**: «всё, что мы тут делаем, очень адаптивно, очень конструктор». То же правило для платежей: из коробки, если можно; нет — адаптируем.
- **Решение:**
  1. **Архитектура не назначает победителя.** Провайдеры — подключаемые адаптеры GoTrue (ADR-03): включение — конфигурация сервиса (client id/secret, redirect-URL), не изменение схемы, RLS или кода фронтов. Вопрос «какой первый» — вопрос развёртывания, а не ТЗ.
  2. **Провайдеры не исключают друг друга.** Включаются одновременно сколько нужно; один аккаунт связывает несколько identities. Провайдер — только «дверь входа»: кошелёк, права и владение данными живут у нас по `user_id`, RLS про провайдера не знает.
  3. **Стартовый — Google** (первый включаемый в M0): в списке провайдеров GoTrue из коробки, покрывает Android. VK и Яндекс — тоже из коробки; включаются той же ценой, когда подтверждён ареал основной аудитории.
  4. **Сбер ID — случай «адаптировать»:** в списке GoTrue отсутствует, возможен только мостом через OIDC-брокер. Имеет смысл лишь вместе с пополнениями через экосистему Сбера — поэтому переносится в платёжный ADR (открытый вопрос 2), отдельно не решается.
  5. **Принцип адаптивности (авторский) фиксируется и для платежей:** интеграция «из коробки» предпочтена собственной; чего в коробке нет — подключается адаптером. Выбор платёжного провайдера остаётся отдельным ADR.
  6. **Критерий адаптивности:** появление нового провайдера не требует миграции, изменения контрактов (5.7) или прав фронтов — иначе это ошибка архитектуры. Секреты и redirect-URL — только в конфигурации окружения, не в коде.
- **Почему:** три из четырёх названных кандидатов уже поддержаны GoTrue — реальный выбор сводится к порядку включения; паттерн повторяет систему: новый воркер = service-аккаунт (ADR-18), новая форма = строка таблицы, новый фронт = те же потоки (FR-IF-3), новый провайдер = строка конфига.
- **Последствия:** FR-AUTH-2 переформулирован (стартовый Google; VK/Яндекс — конфигурация); деплой M0 обязан нести секреты провайдеров в переменных окружения; пункт «Не решено» про OAuth закрыт; платёжный вопрос остаётся открытым и ссылается на принцип адаптивности.

## ADR-26 · Платежи: единый контракт депозита — пользователь платит нашему ядру, провайдер за кадром

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** последний незакрытый контракт — реальные платежи. Предложение автора — три разреза: **кто платит** (пользователь платит нашему ядру, а не провайдеру), **за что и сколько** (пополнение баланса, а не тарифы), **что произошло** (событие провайдера). Нет тарифов и подписок — есть пополнение баланса; Сбер ID возможен только в связке со своей платёжной экосистемой (ADR-25).
- **Решение:**
  1. **Разрез «кто платит» — уже сделан.** Пользователь и его кошелёк живут по `user_id`; провайдерский «паспорт» (cus*Stripe*… и т.п.) — мусор адаптера: в ядре его нет, ссылки на провайдера не пересекают границу контракта. Смена провайдера не трогает пользователей, кошельки и историю.
  2. **Разрез «за что и сколько» — новая сущность депозит.** Универсальный инвойс в таблице `deposits`: пользователь, сумма в фиате + сумма в GC, провайдер, статусы `created → awaiting_payment → paid | failed | expired`. Поправка к источнику (ADR-11): нет тарифов/подписок — есть пополнение баланса; инвойс несёт обе суммы сразу; **курс фиксируется в депозите при создании** — число в конфиге (значение курса утверждено позже — ADR-28: по умолчанию 1:1). Зачисление — только RPC одной транзакцией: депозит → `paid` + запись в `transactions` + баланс (ADR-06/20). Никакого баланса напрямую из вебхука.
  3. **Разрез «что произошло» — единое ухо.** Один webhook-endpoint на систему; адаптер проверяет подпись банка (система никому не верит — принцип ADR-24) и переводит крик провайдера в универсальные события `DEPOSIT_PAID` / `DEPOSIT_FAILED`. Принятое пишется append-only в `payment_events` с уникальным ключом — повтор вебхука безвреден (at-least-once, как outbox — ADR-05).
  4. **«Слепое пятно» — принято дословно.** Нестыкуемые детали протоколов провайдеров складываются в `meta` JSONB депозита: ядро туда не смотрит, переезд между провайдерами историю не ломает.
  5. **Демо-пополнение «из воздуха» = встроенный провайдер.** Кнопка демо-начисления проходит тот же контракт депозита: адаптер мгновенно отвечает `DEPOSIT_PAID` — первый тест абстракции. Реальный провайдер = новый адаптер + строка конфига, ядро не трогаем. Сбер подключается здесь — платёжным адаптером.
- **Почему:** три разреза разделяют то, что меняется по разным причинам: «кто платит» закреплён давно (`user_id`), «за что» — единственная новая сущность, «что произошло» — единственная точка входа внешних сигналов. Один контракт закрывает и демо, и реальный эквайринг: система с первого дня живёт в той же схеме, в которой будет жить с деньгами.
- **Последствия:** таблицы `deposits` и `payment_events` — в эскизе модели (раздел 7), появляются в M1; FR-BILL-2 переформулирован (депозит), FR-BILL-8 добавлен (единое ухо); поток «Пополнение» — 5.7; выбор конкретного провайдера — решён ADR-31: первый провайдер — собственный «ПромоКод»; критерии выбора реального эквайринга (ареал аудитории, «из коробки», СБП/карты, комиссии) остаются для следующих уровней.

## ADR-27 · Валюты: справочник со стабильными id; внутренние и внешние; целевые кошельки сервисов

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** требование автора: валюту надо уметь настраивать; возможны многие валюты внутри приложения; **курсы и обозначения могут меняться — id остаётся**; несколько внешних валют, в которых пользователь платит, и одна внутренняя универсальная, в которую они конвертируются; возможны и **несколько внутренних валют** — минимум, поддержка одной; воркеры могут списывать разные валюты со своими лимитами — «в виде разных целевых кошельков».
- **Решение:**
  1. **Валюта — строка справочника, не константа в коде.** Справочник `currencies`: стабильный **id** (не меняется никогда), вид — внутренняя/внешняя, код и символ — обозначение, меняется свободно. Принцип голого id (ADR-15), применённый к валютам: переименование или смена символа не трогает ни одной ссылки — депозиты, цены и транзакции ссылаются на id.
  2. **Внешние — сколько угодно, но только на входе.** Пользователь платит в чём угодно; конвертация во внутреннюю происходит один раз, при создании депозита (ADR-26); кошельков во внешних валютах нет — внутри системы ходят только внутренние. Курсы — в конфиге (правило «все цифры в конфиге») и фиксируются в депозите; когда валют станет много и курсы начнут меняться часто — допишется история курсов отдельной таблицей, контракты не изменятся.
  3. **Внутренних — сколько нужно, минимум одна (GC).** Кошелёк = «владелец × валюта»: у пользователя по кошельку на каждую внутреннюю валюту; минимум — один GC-кошелёк. Цена формы несёт свою валюту. Конверсию между внутренними не вводим — понадобится, отдельный ADR. Минимум и максимум ложатся на одну схему: различие только в числе строк справочника.
  4. **Воркер — своя валюта, лимит, целевой кошелёк.** Регистрация сервиса (ADR-18) объявляет валюту списания, лимит цены и целевой кошелёк. Списание за задачу — перевод: с кошелька пользователя **на целевой кошелёк сервиса**; журнал показывает «от кого → кому», выручка сервиса видна по его кошельку. Лимит проверяется при публикации формы (цена ≤ лимита сервиса) — на создании задачи отдельной проверки нет: цена приходит из зафиксированной версии шаблона (ADR-19), уже прошедшей лимит; новый код отказа не вводится.
- **Почему:** требования ложатся на принятые паттерны один в один, как платежи (ADR-26): настройка валюты = строка справочника; смена обозначений не ломает историю (голый id); множественность внешних изолирована в точке входа (депозит); множественность внутренних — просто ещё строки справочника; целевые кошельки дают воркерам разные валюты и лимиты без нового механизма денег.
- **Последствия:** справочник `currencies` и валютные поля — в эскизе модели (раздел 7): кошелёк и цена формы ссылаются на валюту, депозит несёт внешнюю и внутреннюю суммы; глоссарий — термины «Валюта» и «Целевой кошелёк»; FR-BILL-1 переформулирован, FR-BILL-9/10 добавлены; M0 создаёт справочник с одной внутренней (GC); значение курса решено позже — ADR-28 (по умолчанию 1:1); открытым остаётся имя платёжного провайдера (открытый вопрос 2). «Своя валюта воркера» уточнена ADR-29: единица учёта затрат с курсом к валюте списания — не кошелёк.

## ADR-28 · Курс: по умолчанию 1:1; маркетинговые пакеты — слой поверх контракта депозита

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** последний открытый пункт денег — значение курса GC (предложение ассистента: 1 GC = 1 ₽ — Запись 5). Ответ автора: по умолчанию — **1:1**; дальше, возможно, появятся **пакеты на покупку внутренней валюты** — тогда надо оставить маркетологам место ставить свои курсы между внешними валютами и внутренней основной. Дополнение автора: **разные воркеры могут менять баланс внутренней валюты**.
- **Решение:**
  1. **Курс по умолчанию — 1 GC = 1 ₽ (1:1).** Значение — параметр конфига, как и было заложено (ADR-26); цена формы читается как рубли. Защита от будущего уже встроена: курс фиксируется в депозите при создании — подъём курса позже не искажает старую историю, у каждого депозита записан его курс.
  2. **Пакеты покупки — маркетинговый слой поверх базового курса, не изменение ядра.** Пакет = предустановленный инвойс: «сумма внешней валюты → сумма GC» с бонусом; у пакета **свой курс поверх базового 1:1**, задаваемый маркетингом. Контракт депозита принимает любой курс — пакет лишь предустанавливает суммы и курс депозита; курсы пакетов живут в конфиге/справочнике («все цифры в конфиге»), не в коде. Идея записана в инбокс; распределена ADR-31 — пакеты: слой платёжного модуля, следующий уровень.
  3. **Баланс внутренней валюты меняют воркеры — но одним рычагом.** Разные воркеры двигают баланс в обе стороны: списание за задачу и возврат при отказе (ADR-22) — каждый в своей внутренней валюте и в пределах своего лимита (ADR-27 п.4). Но сам воркер в баланс не пишет: любое изменение — перевод через RPC с записью в `transactions` (ADR-06/20), с кошелька пользователя на целевой кошелёк сервиса. Прямого рычага воркера на баланс не существует — сколько бы воркеров ни было, защита денег одна.
- **Почему:** 1:1 делает цены читаемыми, а механизм (конфиг + фиксация в депозите) уже защищает историю от смены курса; пакеты укладываются в критерий адаптивности (ADR-25 п.6) — новое предложение маркетинга = строка конфига, ядро не меняется; по балансу защита денег не зависит от числа воркеров — рычаг один, RPC.
- **Последствия:** открытый вопрос 2 спеки теряет «утвердить курс» — в деньгах остаётся только имя провайдера; инбокс: пункт курса закрыт, открыт пункт «пакеты покупки GC»; поток «Пополнение» (5.7) и эскиз модели упоминают курс по умолчанию 1:1 (ADR-28). Списание воркером уточнено ADR-29: резерв при создании, расчёт по факту — системный бухгалтер в RPC фиксации результата.

## ADR-29 · Биллинг по факту: резерв при создании, счёт воркера в своих единицах, системный бухгалтер при фиксации

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** фиксированная цена (ADR-19/22/27) честна для задач с известной стоимостью, но не для воркеров с плавными затратами (токены, GPU-секунды): владельцу сервиса приходится закладывать худший случай в цену — пользователь переплачивает в среднем. Предложение автора («придумал наконец-то»): воркер может иметь **свою валюту** — оценивает затраты по завершении работы и **выставляет счёт в своих единицах**, отдавая данные системе учёта (денег, токинов, затрат); шлюз **резервирует** под задачу определённое количество внутренней валюты; после завершения **системный бухгалтер** пересчитает по факту и курсу и подведёт баланс. «Мне кажется, так будет честно».
- **Решение:**
  1. **Две половины предложения — один механизм.** «Счёт в своих единицах» и «резерв с пересчётом по факту» — не альтернативы, а стороны одной схемы: создание резервирует, воркер считает затраты в своих единицах, бухгалтер переводит их в деньги и подводит баланс. Это схема «авторизация → захват» из платёжного мира — зеркальная к собственному депозитному контракту (ADR-26), теперь внутри наших денег.
  2. **Своя валюта воркера — единица учёта, не кошелёк.** Регистрация сервиса (ADR-18/27) объявляет единицу затрат (токены, GPU-секунды…) и её курс к валюте списания. Единицы не заводят кошельков: кошельки остаются только во внутренних валютах (ADR-27), целевой кошелёк сервиса копит выручку в валюте списания. «Своя валюта» воркера — мерка, а не деньги.
  3. **Резерв вместо списания при создании.** Создание задачи резервирует цену шаблона — теперь это потолок: `reserved` кошелька растёт, доступный баланс падает, списания нет; не хватает доступного — откат, задачи нет (как и было, FR-BILL-3). Потолок и курс единицы фиксируются в задаче при создании — тот же приём, что курс в депозите (ADR-26/28): смена курса сервиса на лету не искажает идущие и старые задачи.
  4. **Счёт — в единицах воркера, деньги считает система.** Воркер по завершении выставляет счёт в своих единицах в отчёте (ADR-20/24). **Системный бухгалтер** — шаг сверки внутри RPC фиксации результата — переводит счёт в валюту списания по зафиксированному курсу, сверяет с резервом и подводит баланс одной транзакцией с вердиктом. Воркер по-прежнему не пишет в баланс ничем и никогда (ADR-28 п.3): он называет затраты, деньги считает система.
  5. **Расчёт и отказы.** `completed`: списание по факту, резерв снимается, остаток освобождается; журнал — `charge` (с единицами и курсом) + `release` остатка. `failed` / `cancelled`: счёта нет — резерв снимается целиком, попытки бесплатны (ADR-22 сохранена). До успешного завершения деньги не покидают кошелёк — «возвращать» больше нечего.
  6. **Крышка: счёт выше резерва не пробивает.** Пользователь не платит больше подтверждённого при создании: расчёт = min(факт, резерв). Фактический счёт в единицах и расхождение видны админу в трассе (ADR-24); потолок задан шаблоном того же владельца сервиса — расхождение внутрисервисное, пользователя не касается.
  7. **Система учёта — существующие таблицы.** Отдельного учёта «денег, токинов, затрат» не заводим: запись `transactions` несёт единицы, курс и сумму; счёт в единицах живёт в трассе. Фиксированная цена становится вырожденным случаем (факт = резерв, `release` пустой) — демо-воркеры и простые формы не меняются.
- **Почему:** честность сходится по всем сторонам — пользователь платит за фактическую работу и никогда больше подтверждённого потолка; воркер получает за фактические затраты по прозрачному зафиксированному курсу; защита денег не слабеет: рычаг по-прежнему один (RPC, ADR-06/28), бухгалтер добавляет пересчёт, но не новый источник правды.
- **Последствия:** FR-BILL-3 переписан (резерв вместо списания), FR-BILL-5/7 — снятие резерва, добавлен FR-BILL-11; матрица 5.9 — колонка денег («в резерве»), сообщения кодов 5.10 — «резерв снят» вместо «деньги возвращены»; эскиз модели: `wallets.reserved`, типы `transactions` (reserve/charge/release + units/rate), `system_tasks.reserved/rate_fixed`, `services.unit/rate`; открытый вопрос 3 (частичный возврат) закрыт — счёт только при успехе; SQL-схема и RPC бухгалтера — цикл M1.

## ADR-30 · Прораб: сторона исполнения на стыке; приём бланка с оценкой времени; попытки с лимитом

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** открытый пункт — попытки выполнения задачи на стыке шлюз ↔ воркер (лимит попыток, поля лока — инбокс). Предложение автора — по аналогии с «единым окном» и бригадой строителей ввести посредника и назвать его (кандидаты: прораб, окно, сервис, контроллер воркеров; «их может быть несколько в системе»), пока — «прораб». Механика: шлюз отдаёт бланк с задачей прорабу; тот возвращает бланк обратно со статусом «принял» и примерным временем на выполнение и запоминает его у себя; при отправке шлюзом того же бланка как следующей попытки прораб заполняет его статусом выполнения, принятым в системе; шлюз пробует 5 раз запросить результат — с утроенным интервалом времени на выполнение задачи; возможно, шлюзу и прорабу надо учитывать среднее время выполнения одной задачи; «получается, прораб-окно может исполнять взятые — предложенные им задачи».
- **Решение:**
  1. **Имя — прораб.** «Окно» занято шлюзом (единое окно — ADR-18), «сервис» — адресатом очереди (`target_service`), «контроллер воркеров» — должностная инструкция, а не имя. Прораб — сторона исполнения на стыке: service-аккаунт за своим `target_service` (ADR-18), его идентификатор и стоит в `locked_by`. Прорабов может быть сколько угодно — разные сервисы и несколько прорабов на один: очередь одна, SKIP LOCKED раздаёт (ADR-08). Исполняет ли прораб задачу сам или раздаёт бригаде — его внутреннее дело: контракт видит одного прораба (NFR-3 не меняется). Берёт он только то, что выдал шлюз, — сам себе задачу не назначает.
  2. **Приём — правило стека с содержанием.** «Шлюз отдал бланк — получил обратно» (ADR-24) пополняется составом ответа: **«принято» + оценка времени (ETA)**. Не принял (перегружен) — бланк возвращается сразу: задача мгновенно снова в очереди, попытка не тратится — попыткой считается принятая работа. Запись приёма — в трассе (ADR-24): админ видит, кто взял и сколько обещал.
  3. **Повтор бланка — отчёт, не повторная работа.** «Прораб запоминает бланк у себя» — дедуп по задаче (ADR-20), тот же приём, что во всей системе: помнящий прораб на повторную доставку того же бланка отвечает текущим статусом из справочника системы (свои статусы не придумываются — ADR-10); потерявший работу (упал) — принимает заново как новую попытку. От памяти прораба корректность денег не зависит: вердикт фиксирует шлюз один раз по состоянию строки (ADR-20/29) — двойного исполнения и двойной оплаты не бывает.
  4. **Ожидание попытки — 3 × оценка.** Лок таймаута (ADR-08) становится динамическим: отчёт попытки ждут 3 × ETA (множитель и потолок — в конфиге, ADR-23; потолок не даёт прорабу купить бесконечное время завышенной оценкой). Оценку называет прораб — он знает свою бригаду; не назвал — шлюз подставляет среднее время сервиса по завершённым задачам. Авторское «возможно, учитывать среднее» — да, по долям: прораб — свою бригаду, шлюз — историю сервиса; таблиц под это не заводим — среднее считается из журнала.
  5. **Попытки — счётчик на задаче, лимит 5.** Молчание дольше ожидания — `WORKER_TIMEOUT`: задача в очередь, попытка +1 (матрица ADR-22 прежняя). Лимит попыток — 5 по умолчанию (в конфиге); исчерпан — failed, `LIMIT_EXHAUSTED`, резерв снимается целиком, попытки бесплатны (ADR-22/29). Новых статусов и кодов отказа нет.
- **Почему:** имя продолжает ряд живых имён системы (бланк, материализатор, бухгалтер) и честно к роли: прораб отвечает за принятую работу, а не тождествен исполнителю; приём с оценкой превращает глобальную константу таймаута в уговор на конкретную задачу; дедуп по бланку, ожидание по оценке и лимит попыток — те же приёмы, что везде (идемпотентность, конфиг вместо констант, реестр кодов); очередь остаётся честной — молчащий прораб не придерживает задачу, она возвращается в общую очередь.
- **Последствия:** глоссарий — «Прораб», «Попытка»; FR-FORM-11/12; матрица 5.9 — `locked_until` по оценке прораба и счётчик попыток; эскиз модели — `locked_until` и `attempts` на `system_tasks`; сообщение `WORKER_TIMEOUT` называет прораба; инбокс — «лимит попыток» и «поля лока» закрыты; контракт claim шлюза (M2) дополняется ответом приёма («принято» + ETA) и повторной доставкой бланка; прорабы одного сервиса — несколько service-аккаунтов с одним `target_service`, связь — в регистрации аккаунта (ADR-18), без новых таблиц.

## ADR-31 · Первый платёжный провайдер — собственный «ПромоКод»; пакеты и лимиты — слой платёжного модуля

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** открытый вопрос 2 — имя первого платёжного провайдера. Ответ автора: первый провайдер — наш собственный, имя «ПромоКод». Назначение: использование для локальной и некоммерческой работы приложения; попутно он проверяет работу платёжного интерфейса; «самое интересное» — оплата как угодно: оплачивать можно в любом месте — пользователь получает промокод и всё. Кассы и онлайн-платежи — опционально, на следующих уровнях.
- **Решение:**
  1. **Первый провайдер — собственный кодовый «Промокод»** (идентификатор `promocode`): пользователь получает промокод (номинал зашит в коде) и гасит его в приложении. Гашение — депозит по контракту (ADR-26): код → депозит с суммами → адаптер проверяет код (валиден, не погашен) → `DEPOSIT_PAID` → зачисление RPC одной транзакцией. Повторное гашение исключается статусом кода — как dedup в `payment_events` (ADR-26).
  2. **«Оплата как угодно, в любом месте» — буквально.** Код — носитель платежа вне любых интерфейсов: продать, подарить, передать лично, напечатать — распространение и маркетинг живут вне ядра; ядро видит только «код предъявлен → погашен».
  3. **Стенд проверки платёжного интерфейса.** Промокод прогоняет весь контракт без внешних систем: депозит, статусы, единое ухо, идемпотентность, зачисление RPC. Демо-кнопка «из воздуха» (ADR-26) остаётся мгновенным тестом; «Промокод» — именованный первый провайдер.
  4. **Пакеты покупки GC и лимиты пополнения — слой платёжного модуля (следующий уровень).** Модуль называет суммы («сколько и чего зачислить»), проводка — только через RPC-бухгалтера системы: рычаг на баланс один (ADR-06/28). Принцип пакета со своим курсом — ADR-28; генерация партий кодов, номиналы и лимиты — детали проектирования платёжного модуля.
  5. **Реальные кассы и онлайн-платежи — опционально, следующие уровни**, по-прежнему адаптерами: включение = адаптер + строка конфига (ADR-25/26), ядро не трогается.
- **Почему:** критерий адаптивности (ADR-25 п.6) уже превратил провайдера в строку конфига — собственный кодовый провайдер самый дешёвый первый адаптер и одновременно проверка контракта в деле; некоммерческий старт не тянет ни внешнего эквайринга, ни его комиссий.
- **Последствия:** открытый вопрос 2 закрыт; FR-BILL-2 переформулирован (демо-кнопка + «Промокод»), FR-BILL-12 добавлен (пакеты и лимиты — платёжный модуль); поток «Пополнение» (5.7) дополнен гашением кода; M1 включает «Промокод» первым провайдером; детали (формат кода, партии, номиналы) — проектный пакет уровня «платёжный модуль» (очередь проектирования, раздел 9).

## ADR-32 · Базовый вход — email/пароль в ядре; OAuth и API-доступ — следующие уровни

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** инбокс «нужен ли вход по email/паролю вообще, или только OAuth + телефон». Ответ автора: базовая регистрация логин/пароль — для внутренней и некоммерческой работы; email — в ядре, OAuth — «не знаю», следующий уровень через контракт. Идея к этому: обеспечить API-доступ по логин/пароль и по refresh/access-токенам.
- **Решение:**
  1. **Базовый вход ядра — email + пароль** (GoTrue из коробки). Достаточно для внутренней и некоммерческой работы; внешний провайдер старту не нужен.
  2. **OAuth — следующий уровень через контракт.** Принцип ADR-25 не меняется — провайдер = конфигурация GoTrue без изменений кода; уточняется только старт: п. 3 ADR-25 (стартовый Google) откладывается, стартовый провайдер OAuth не назначается до своего уровня.
  3. **API-доступ (логин/пароль → access/refresh) — идея зафиксирована.** GoTrue выдаёт пару access/refresh из коробки — механика совпадает с идеей; нового механизма не строим, сверимся при проектировании уровня API-доступа.
  4. **Профиль: базовое — в ядре, остальное — расширению.** Аватарка (Storage) и отображаемое имя — ядро; расширенный профиль ведёт «аккаунтер» — расширение, продолжающее ряд живых имён (бухгалтер — деньги, аккаунтер — аккаунт). Контур и состав расширенного профиля — следующий уровень.
- **Почему:** некоммерческий старт не требует внешних провайдеров; дверь OAuth уже построена (ADR-25) — включение позже не меняет ни схемы, ни фронтов; профиль разбит на «ядро минимум» и «расширяемое» по тому же правилу адаптивности.
- **Последствия:** FR-AUTH-2 переформулирован (базовый вход email/пароль, OAuth — следующий уровень); FR-AUTH-4 уточнён (базовый профиль — ядро, расширенный — «аккаунтер»); глоссарий — «Аккаунтер»; инбокс «email vs OAuth» и «профиль» закрыты; уточнение ADR-25 отмечено в его статусе.

## ADR-33 · Этапы проектирования: аналитика → контракты → проектирование → реализация

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** вопрос автора: «есть ли у нас система этапов проектирования? если нет — внедрить». Установка рядом: кода на этапе анализа не писать — так меньше контекста и меньше переделывать; продолжаем бизнес-аналитику: требования и контракты. Имелись циклы реализации (M0–M4) и поток «идея → обсуждение → решение», но ступени между решением и кодом явно не названы.
- **Решение:** проектирование — четыре ступени, код последняя:
  1. **Аналитика (бизнес-уровень).** Инбокс → обсуждение → ADR и требования спеки. Выход — решения «что и зачем».
  2. **Контракты (системный уровень).** Потоки (5.7), реестры (статусы, коды, события), границы акторов. Выход — разделы спеки: «кто с кем о чём договаривается».
  3. **Проектирование (уровень работ).** Для очередного уровня — детальные контракты: SQL-схема, сигнатуры RPC, JSON Schema, состав конфига. Выход — проектный пакет в `docs/`; кода ещё нет.
  4. **Реализация (циклы M0–M4).** Код по зафиксированным контрактам; расхождение — правим контракт и код вместе (ADR-04).
     Правило: **цикл не открывается, пока его проектный пакет (ступень 3) не зафиксирован в docs.** Очередь тем проектирования — раздел 9 спеки.
- **Почему:** установка автора «меньше контекста и меньше переделывать» превращена в структуру; ступени 1–2 и 4 фактически уже жили (инбокс/ADR, потоки/реестры, циклы) — введена недостающая ступень 3, которая раньше существовала неявно (эскиз модели, реестры кодов).
- **Последствия:** до старта M1 собирается его проектный пакет (SQL-схема, RPC резерва и бухгалтера, состав конфига); темы «следующих уровней» — очередь в разделе 9 спеки; прототип (ADR-04) остаётся эталоном механики между ступенями 2 и 4.

## ADR-34 · Формы предоставляются стороной исполнения; единый контракт типов и материализатора — следующий уровень

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** автор: формы фактов и формы задач — то, что предоставляют нам воркеры/прорабы и вся эта система при добавлении их в систему; «они знают всё про них». Надо разработать единый контракт для базовых типов и правила их объединения и контракт материализатора. Это следующий уровень — когда будем рассматривать связь UI и воркеров, где наша центральная часть для них выглядит прозрачной.
- **Решение:**
  1. **Источник форм — сторона исполнения.** Форму даёт сервис (прораб/воркер) при добавлении в систему: он знает свою предметку; система валидирует и публикует. На старте циклов, пока контракта регистрации нет, формы заводит админ вручную в БД — открытый вопрос 4 закрыт.
  2. **Единый контракт базовых типов** — словарь примитивов (FR-FORM-9) и правила их объединения: разрабатывается проектным пакетом следующего уровня «связь UI ↔ воркеры» (ADR-33).
  3. **Контракт материализатора** — в тот же пакет: что шлюз собирает из фактов и файлов и что получает прораб.
  4. **Прозрачность ядра.** Критерий уровня — авторская формула: для стороны исполнения центральная часть прозрачна — сервис живёт своим контрактом (формы, claim, отчёт), ядро не видно (усиление NFR-3, ADR-18).
- **Почему:** единый контракт = одна валидация, один рендер, одна маршрутизация (ADR-07/10); назначение автора форм закрывает последний «чей это» вопрос контракта; форма от сервиса согласована с лимитом и ценой регистрации (ADR-27) — публикует систему, а не фронт (ADR-12).
- **Последствия:** FR-FORM-7 помечен инструментом старта/правки, FR-FORM-9 — базой контракта типов; тема — в очереди проектирования (раздел 9); поток регистрации сервиса при своём уровне пополняется «передачей форм».

## ADR-35 · Открытый словарь типов: примитивы + типы-расширения + тип-список; микс — особый тип

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** развитие ADR-34: автор попросил проработать «самый важный аспект — форму бланка»: к базовым типам добавить тип-расширение (возможность добавлять неограниченное количество составов из базовых типов) и тип-список (много однотипных форм). Предложенный контракт: примитивы — закрытый набор ядра; тип-расширение — именованный состав полей из примитивов и других расширений, строка в БД, версии append-only, объявляет сторона исполнения; тип-список — контейнер с одним объявленным типом элемента, min/max в схеме, значение — JSON-массив. Три вопроса автору: однородность списков, вложенные списки, владелец типов. Ответы автора: циклы запрещены; микс возможен в особом типе — добавить тип, и материализатор его пропускает; неоднородность запрещена; материализовать надо только то, что написано в бланке.
- **Решение:**
  1. Словарь трёхслойный: **примитивы** (text, number, bool, date, select, fact_ref, file — закрытый набор) → **типы-расширения** (именованные составы, версии append-only) → **тип-список** (однородный массив элементов одного объявленного типа). Новый тип = строка в БД, не релиз.
  2. **Неоднородность запрещена** (ответ автора): список хранит элементы одного объявленного типа.
  3. **Микс — особый тип** (ответ автора): неоднородное содержимое допускается только в специальном типе «микс» — ещё одна строка словаря; материализатор его пропускает: не разворачивает и не проверяет, содержимое уходит в бланк как написано. Лазейка одна и явно названа.
  4. **Циклы запрещены** (ответ автора): расширение не ссылается на себя прямо или через цепочку — проверка при регистрации типа.
  5. **Материализуется только то, что написано в бланке** (ответ автора): материализатор работает строго по значениям values — не достаивает пустые поля и не разворачивает ничего сверх написанного.
  6. Ограждения без возражений приняты: списки — только на верхнем уровне формы (вложенных списков нет в принципе); версия типа фиксируется в задаче вместе с версией шаблона (ADR-19); цена не зависит от длины списка (потолок резерва — ADR-29); потолки (макс. элементов, глубина составов) — числа в конфиге.
- **Почему:** открытый словарь повторяет главный паттерн системы — новая сущность = строка, не релиз (форма — ADR-07, воркер — ADR-18, провайдер — ADR-25). Однородность плюс единственный явно названный микс-тип держат валидацию и материализатор простыми; «только написанное» продолжает дисциплину снимка (ADR-14): воркеру уходит ровно то, что зафиксировано, и ничего сверх.
- **Последствия:** FR-FORM-9 дополнен, матрица примитивов — примечание о составных типах и миксе; глоссарий — «Тип-расширение», «Тип-список», «Микс»; «гирлянды фактов» из инбокса закрыты (список с элементом fact_ref = список ссылок на факты), дерево вложенности фактов остаётся отложенным; открытый хвост — владелец типов (общие vs сервисные) — перенесён в обсуждение бланков.

## ADR-41 · Подбланки: конверт делится на подбланки с общим id; требования формы — в бланке; meta_ui и ошибки — отдельно

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** обсуждение бланков (повестка 3 и 5: состав конверта, кто задаёт meta_ui, как ошибки валидации возвращаются к полям). Ответ автора: **все требования к формам должны быть прописаны в бланке**; бланк можно разделить на несколько подбланков, объединённых одним id — «по возможности всё прописать в бланках»; **meta_ui и ошибки отделить от основного бланка**.
- **Решение:**
  1. **Требования формы — в бланке, не в коде интерфейса.** Всё, что нужно любому фронту, чтобы нарисовать и проверить форму, — поля, типы, обязательность, маски, виджеты, правила — приезжает в бланке (шаблоне) из словаря типов (ADR-34/35). Интерфейс — чистый рендерер: усиление ADR-10/12, домен-логики на фронте нет и появиться не может.
  2. **Конверт — семейство подбланков с общим id бланка.** Основной бланк (system, values, commands) и подбланки-спутники: **meta_ui** (как показать) и **ошибки к полям** (валидационные замечания) — отделены от основного бланка и связаны его id. Правило ADR-10 «бланк иммутабелен между шагами» теперь дёшево: меняются подбланки, основной бланк не трогается.
  3. **Граница отделения.** Отделяются meta_ui и именно ошибки к полям — повторяемые, меняющиеся данные. Вердикт системы (код из реестра 5.10, ADR-24) остаётся в конверте задачи — он один на задачу и не протухает.
  4. **Транспорт и точный состав подбланков** (что в каком подбланке, чем едут: REST-ответ или realtime-событие, кэширование meta_ui) — детализация проектного пакета «Бланки» (ступень 3, ADR-33).
- **Почему:** разделение идёт по частоте изменений: основной бланк неизменяем, meta_ui стабилен в рамках версии шаблона и кэшируется, ошибки живут одну валидацию; общий id держит семейство собранным — подбланки не теряют друг друга ни в потоках 5.7, ни в локальной базе клиента (ADR-23). «Всё в бланках» продолжает главный принцип: система ничего не знает о UI, но отдаёт всё, что UI нужен (ADR-40).
- **Последствия:** поток 2 (5.7) читается как «основной подбланк + подбланк meta_ui, общий id»; FR-IF-2 переформулирован — ошибки к полям приходят отдельным подбланком; глоссарий — «Подбланк»; состав и схемы подбланков — JSON Schema в проектном пакете «Бланки».

## ADR-42 · Черновики: любая начатая форма сохраняется; файл — собственность пользователя с момента загрузки

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** повестка бланков 4 и 6 (состояния бланка у пользователя, файлы до постановки задачи). Ответ автора: у пользователя **любую начатую форму сохраняем** (механики пока не назвал — «тут сразу ничего не знаю»); про файлы — **если загрузил файл, то это его файл, даже если не дозаполнил форму**; начал вписывать и не дописал — тоже сохранено.
- **Решение:**
  1. **Черновик бланка сохраняется всегда.** Начатое заполнение — ввод и загруженные файлы — не теряется: форма не дозаполнена, страница закрыта, связь пропала — черновик ждёт пользователя. Принцип «потерять начатое нельзя» зафиксирован; где живёт черновик (локально в IndexedDB / на сервере, как синхронизируется) и его ретеншн — открытые вопросы пакета «Бланки».
  2. **Файл — собственность пользователя с момента загрузки.** Загрузка сразу делает файл полноценным: Storage + реестр `files` с владельцем-пользователем; судьба формы на владение не влияет. Форма брошена — файлы остаются у владельца; удаление — только его решение (tombstone, ADR-16) или админ.
  3. **Родитель файлов черновика — черновик бланка** (механизм происхождения FR-FILE-7 без изменений: реестр знает родителя и `field_code`).
  4. **Квота честная:** файлы черновиков считаются в общем объёме пользователя (FR-FILE-3, ADR-39) — брошенные черновики не прячутся от квоты.
  5. Состояния бланка у пользователя: черновик (это решение) и «шаблон» — предзаполненный бланк, не протухающий по ADR-37; полная машина состояний — в пакете «Бланки».
- **Почему:** принцип офлайн-first (ADR-09/23) доведён до заполнения форм: пользователь не платит вниманием за обрыв сети; владение файлом с момента загрузки снимает класс потерь «загрузил — форма не отправилась — файл исчез» и не требует отдельного «хранилища временных файлов» — файлы черновиков живут в том же реестре по тем же правилам (ADR-16).
- **Последствия:** FR-FORM-15 (черновики сохраняются), FR-FILE-9 (владение файлом с момента загрузки, родитель — черновик, квота); критерий приёмки 5.4 дополнен; открытые пункты пакета «Бланки»: хранение черновиков, ретеншн черновиков и брошенных файлов.

## ADR-36 · Приоритеты очереди: пользователи и группы; единица очереди — вектор

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** инбокс «платные задачи раньше?» — вопрос дважды оставался без ответа (Запись 10 — «без ответа»). Ответ автора: тема интересная и поднимает важные вопросы. Приоритет можно ставить между пользователями и между разными группами задач одного пользователя, но строго соблюдать очерёдность задач в одной группе задач. Группа задач — разновидности деревьев/графов; в «коробку» (очередь) берём группу задач в виде вектора задач и штучную задачу как вектор единичной длины; остальные варианты — записать в память (например: граф задач начинается из листьев — листья выполняются независимо, узел должен быть выполнен по завершении листьев).
- **Решение:**
  1. Приоритет живёт на двух уровнях: **между пользователями** и **между группами задач одного пользователя**.
  2. **Внутри одной группы — строгая очерёдность**, не нарушается никогда: группа исполняется в порядке следования задач.
  3. Единица постановки в очередь — **вектор**: группа задач или одиночная задача (вектор длины 1). SKIP LOCKED (ADR-08) раздаёт задачи с учётом приоритетов уровней и порядка внутри вектора.
  4. Отдельного правила «платные задачи раньше» решение не вводит: порядок определяют уровни приоритета и очерёдность внутри группы.
  5. **Графы задач — в память (инбокс), первая версия их не строит:** зависимости «узел после листьев» — идея следующего уровня, если потребуется.
- **Почему:** модель «пользователь → группа → задача со строгим порядком внутри» закрывает вопрос без нового механизма: очередь остаётся одной (Postgres, SKIP LOCKED), приоритет — поля и порядок выдачи. Графы зависимостей ломают правила «одна задача — один бланк — один вердикт» (ADR-13/24) и биллинг резерва — поэтому в память, не в первую версию.
- **Последствия:** FR-FORM-13; поля приоритета (уровень пользователя, порядок группы) — проектный пакет очереди/исполнения; идея «графы задач» записана в инбокс; инбокс-пункт «приоритеты очереди» закрыт.

## ADR-37 · Ретеншн задач-бланков: 14 дней из коробки, состояние «шаблон» не протухает

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** вопрос 5 спеки — сколько хранить сами задачи-бланки (файлы и версии фактов решены — ADR-17). Ответ автора: из коробки 14 дней задачи в любом состоянии, кроме состояния «шаблон» (предзаполненный бланк).
- **Решение:**
  1. Задачи-бланки хранятся **14 дней из коробки** — в любом состоянии (pending, processing, completed, failed, cancelled).
  2. Исключение — состояние **«шаблон»** (предзаполненный бланк): такие задачи ретеншном не удаляются.
  3. Число дней — в конфиге («все цифры в конфиге»); чистит фоновое задание — как TTL трассы (ADR-24).
- **Почему:** правило одной цифрой закрывает вопрос 5 спеки; «шаблон» — заготовка пользователя для повторного заполнения, это данные, а не мусор.
- **Последствия:** FR-FORM-14; вопрос 5 раздела 9 закрыт; что именно удаляется вместе с задачей (materialized-снимок, вердикт, результат, трасса) — деталь проектного пакета (ступень 3, ADR-33); с файлами и фактами ретеншн задач не пересекается — там свои правила (ADR-16/17).

## ADR-39 · Лимиты файлов: админ-панель по типам; главный показатель — общий объём пользователя

- **Дата:** 2026-06 · **Статус:** принято
- **Контекст:** FR-FILE-3 (C) — нужна цифра лимита одного файла. Ответ автора: сделать админ-панель настроек по типам файлов; должны обеспечивать размер фото телефона, видео/аудио на 5 минут — все привыкли к голосовым сообщениям и «кружочкам»; точные размеры считает/настраивает админ-панель; основной показатель — общий объём пользователя, он важнее размера единицы контента.
- **Решение:**
  1. Лимиты — **настройки админ-панели по типам файлов** (цифры в конфиге, админ-панель — их редактор).
  2. Дефолты «из коробки» вмещают фото телефона и аудио/видео ≈ 5 минут (голосовые, «кружки»); точную нарезку типов и цифр задаёт админ.
  3. **Главный показатель — общий объём пользователя** (квота, FR-FILE-7): он важнее размера единицы контента.
- **Почему:** тип контента уже в реестре файлов (mime — ADR-16), поэтому «по типам» ложится без новой сущности; объёмная квота защищает хранилище лучше, чем лимит единицы, и уже принята (ADR-17).
- **Последствия:** FR-FILE-3 — приоритет S, переформулирован; дефолтные нарезки типов — конфиг старта; админ-экран получает редактор лимитов.

- **Контекст:** ответы автора по корзине 1 частично решают вопрос, частично переводят его на другой уровень; корзина 2 принята целиком — шесть пунктов инбокса закрыты формально: цена в схеме шаблона (FR-FORM-1, ADR-19/29); валидация — сервер, JSON Schema (ADR-07/24); прототип = админ-панель (ADR-04, цикл M4); корзины файлов (task-files, fact-files, result-files, avatars — раздел 7); «10 000 пользователей» — NFR-5; глубина ссылок факт → факт — «гирлянды» закрыты ADR-35.

  1. **Публикация форм («черновик / опубликована», кто публикует каталог)** — в обсуждение бланков, текущий поток аналитики (пакет открыт).
  2. **Что видит гость до входа, PWA/офлайн-режим, push о готовности — уровень UI** (очередь проектирования). Принцип автора зафиксирован: из коробки — одностраничный сайт; сервер-ядро ничего не знает о UI, но должна быть готова отдать всё на UI в рамках одного пользователя (усиление FR-IF-3).

- **Последствия:** инбокс переразложен, корзина 2 снята; очередь проектирования (раздел 9) пополнена уровнем UI; FR-BILL-4 дополнен пользовательским видом журнала; FR-OFF-3 — пометка «решение уровня UI»; открыт пакет «Бланки».

## ADR-43 · Стек: ядро — Go, воркеры — Python; Supabase не используется

- **Дата:** 2026-09 · **Статус:** принято; заменяет ADR-03
- **Контекст:** рабочие документы (`CLAUDE_TASK_BRIEF.md`, `CLAUDE_ROADMAP.md`) описывали ядро на Python, спецификация OFFGRID — на Supabase (ADR-03). Автор: «несмотря ни на что стек у нас на Go — мне надо быть уверенным в большую нагрузку на будущее; то, что везде пишут про Python, забываем; Python — только в воркерах».
- **Решение:**
  1. **Ядро — Go**: реестр модулей, матрица «статус × команда», материализатор, биллинг и бухгалтер, очередь, шлюз воркеров, outbox, realtime, авторизация.
  2. **Python — только в воркерах** (прорабах): Taleweaver, алгоритмы монолита, СПА, тьюторы. Воркер — отдельный процесс/контейнер, общается с ядром только через шлюз (ADR-18, ADR-45).
  3. **Supabase не используется.** PostgreSQL остаётся единственным хранилищем и единственной очередью (ADR-08); деньги — только транзакциями Postgres, одна транзакция на «резерв + задача + outbox» (ADR-06/29 в силе). Логика денег — в Go-коде внутри транзакции, а не в RPC-функциях Supabase.
  4. **Режим `in_process`** манифеста доступен только Go-модулям, собранным вместе с ядром; любой Python-модуль — `worker_service`.
- **Почему:** Go даёт предсказуемую производительность и дешёвую конкурентность под целевую нагрузку (ADR-50); граница «ядро ↔ воркер» уже проведена контрактом шлюза (ADR-18) — язык воркера ядру безразличен.
- **Последствия:** контракты ядра — языконезависимые (JSON Schema, OpenAPI); Python-протоколы `contracts/interfaces/base.py` и `contracts/events/core_events.py` удалены; Python-SDK воркера — отдельный шаг; авторизация — ADR-44; realtime — ADR-46.

## ADR-44 · Авторизация — своя в Go: email/пароль, JWT access + refresh

- **Дата:** 2026-09 · **Статус:** принято; уточняет ADR-25/32 (GoTrue больше не используется)
- **Контекст:** с уходом Supabase (ADR-43) нужен источник логина и сессий. Варианты: своя реализация в Go или GoTrue отдельным контейнером. Выбор автора — своя.
- **Решение:** ядро само ведёт пользователей: email + пароль (хэш argon2id), короткоживущий access-JWT и refresh-токен (ротация при обновлении, хранение хэша refresh в БД, отзыв при выходе). OAuth-провайдеры — адаптеры следующего уровня (принцип ADR-25 п.6: новый провайдер не меняет контрактов). Секреты подписи — только в переменных окружения.
- **Почему:** одна кодовая база и одна БД; идея API-доступа по access/refresh (ADR-32 п.3) закрывается той же механикой.
- **Последствия:** таблицы `users`, `refresh_tokens` — в проектном пакете M0; стейтлесс проверка access-JWT на любом инстансе (ADR-50).

## ADR-45 · Шлюз воркеров — HTTP/JSON: claim → accept(ETA) → heartbeat/progress → commit

- **Дата:** 2026-09 · **Статус:** принято; конкретизирует ADR-18/20/30
- **Контекст:** Python-воркеры (ADR-43) общаются с Go-ядром. Варианты — HTTP/JSON или gRPC. Выбор автора — HTTP/JSON.
- **Решение:** контракт шлюза — `contracts/interfaces/worker_gateway.openapi.yaml`:
  1. `POST /claim` — прораб (service-токен, ADR-18) берёт задачу своего `target_service` и версии (SKIP LOCKED, ADR-08/19); ответ — materialized-бланк или «пусто».
  2. `POST /tasks/{id}/accept` — «принято» + ETA; `locked_until = now + 3 × ETA` с потолком из конфига; отказ в приёме — задача сразу в очередь, попытка не тратится (ADR-30).
  3. `POST /tasks/{id}/heartbeat` и `POST /tasks/{id}/progress` — прогресс эфемерен, в БД не пишется (FR-FORM-4).
  4. `POST /tasks/{id}/commit` — отчёт по JSON Schema; фиксация `WHERE status='processing' AND locked_by=прораб`, 0 строк — вернуть текущее состояние (ADR-20); мусор → `REPORT_INVALID` (ADR-24).
- **Почему:** бланк — JSON (ADR-10), HTTP/JSON передаёт его без перекодирования; Python-клиент тривиален, отладка — curl. gRPC возможен позже как второй транспорт того же контракта.
- **Последствия:** Python-SDK воркера реализует этот контракт; шлюз — часть Go-ядра.

## ADR-46 · Realtime: WebSocket на каждом инстансе, фанаут через Postgres LISTEN/NOTIFY

- **Дата:** 2026-09 · **Статус:** принято; конкретизирует ADR-05/23
- **Контекст:** под нагрузку (ADR-50) ядро работает несколькими инстансами; сокет пользователя висит на одном из них, а событие рождается на любом. Варианты фанаута — Postgres LISTEN/NOTIFY или NATS. Выбор автора — LISTEN/NOTIFY.
- **Решение:** outbox-демон берёт записи `outbox_queue` (SKIP LOCKED), назначает `seq` на пользователя и делает `NOTIFY` с идентификатором события; каждый инстанс слушает канал (`LISTEN`) и отдаёт событие своим сокетам этого пользователя. Полезная нагрузка NOTIFY — только ссылка (id/seq), тело читается из БД (лимит payload NOTIFY — 8 КБ). Прогресс (`task.progress`) идёт тем же каналом, но без outbox — эфемерно. Heartbeat, backoff, snapshot + догоняющие — по ADR-23.
- **Почему:** ADR-08 — «очередь одна, брокера нет»; Postgres уже есть, новая инфраструктура не нужна; для 10 000 пользователей объём событий укладывается в LISTEN/NOTIFY с запасом.
- **Последствия:** реестр событий — `contracts/events/realtime_events.schema.json`; при росте за пределы одного Postgres — отдельный ADR на брокер.

## ADR-47 · Учёт воркера: основная единица + дополнительные, конвертируемые в основную

- **Дата:** 2026-09 · **Статус:** принято; уточняет ADR-29
- **Контекст:** ADR-29 даёт воркеру одну единицу учёта. Taleweaver тратит три ресурса: токены LLM, картинки, секунды озвучки. Решение автора: сделать дополнительные единицы, конвертируемые из основной.
- **Решение:**
  1. Манифест объявляет `worker_accounting.base_unit {name, rate_gc}` — основная единица и её курс к валюте списания — и `extra_units [{name, rate_to_base}]` — дополнительные единицы с курсом к основной (Taleweaver: base = `tokens`; `images` и `tts_seconds` — через `rate_to_base`).
  2. Счёт воркера (`report.worker_charge`) — строки `{unit, units}` по любым объявленным единицам; единица вне манифеста → `REPORT_INVALID`.
  3. Бухгалтер: `base_units = Σ units × rate_to_base` (для основной — 1), `total = base_units × rate_gc`, списание `min(total, резерв)` (ADR-29 п.6).
  4. Все курсы (`rate_gc`, `rate_to_base`) фиксируются в задаче при создании — смена курса на лету не искажает идущие задачи (ADR-29 п.3).
- **Почему:** кошелёк и бухгалтер остаются с одной мерой (основной единицей) — меняется только разбор счёта; новый ресурс воркера = строка манифеста.
- **Последствия:** `module_schema.json` и `blank_envelope_schema.json` (секция `report.worker_charge`) переписаны; `system_tasks.rate_fixed` хранит набор курсов.

## ADR-48 · Вердикт — только коды реестра; статусы задач и фактов — раздельные справочники

- **Дата:** 2026-09 · **Статус:** принято; уточняет ADR-22/24
- **Контекст:** `blank_envelope_schema.json` нёс собственный набор вердиктов (`VALIDATION_FAILED`, `EXECUTION_ERROR`, `TIMEOUT` …), расходящийся с реестром 5.10, и один список из девяти статусов для фактов и задач вперемешку. Автор: коды — как в реестре; статусы могут быть отдельными; сама задача — тоже некий факт.
- **Решение:**
  1. `report.verdict` = `SUCCESS` либо код из реестра 5.10: `INSUFFICIENT_FUNDS, VALIDATION_ERROR, FACT_NOT_PUBLISHED, FACT_MISSING, FILE_MISSING, WORKER_TIMEOUT, LIMIT_EXHAUSTED, WORKER_ERROR, REPORT_INVALID, COMMAND_REFUSED`. Новый код — только новой строкой реестра (ADR-24 п.3).
  2. Статусы — по виду бланка: **задача** — `draft, template, pending, processing, completed, failed, cancelled` (`draft` — ADR-42, `template` — ADR-37; жизненный цикл очереди — ADR-22); **факт** — `draft, published, archived, deleted` (ADR-15). Схема конверта проверяет статус в паре с `system.kind`.
  3. «Задача — тоже факт» читается через принятое: результат завершённой задачи оформляется факт-бланком `origin=task` (ADR-15 п.4), а сама задача после завершения неизменяема (ADR-14).
- **Последствия:** `blank_envelope_schema.json` переписан; тесты матрицы используют только коды реестра.

## ADR-49 · Ядро доменно-агностично: предметная область — у воркеров

- **Дата:** 2026-09 · **Статус:** принято; усиливает ADR-34
- **Контекст:** спецификация тьюторов предлагала обезличивание ПДн материализатором ядра — это требует от ядра знания предмета. Автор: ядро не должно знать предметную область; она — у воркеров, либо переделать тьюторов.
- **Решение:** ядро видит только конверт, типы полей (ADR-35), реестры, деньги и маршруты. Смысловая валидация, обезличивание, расчёты, объяснения (`explanation`, `evidence`, `data_gaps`) — у воркера/модуля; предметные поля живут в `values` и `report` (секция `report` открыта для дополнительных полей). Кейс тьюторов переделывается: данные ребёнка попадают в систему уже под обезличенным кодом, ПДн — зона модуля тьюторов.
- **Последствия:** `docs/specifications/04_case_tutor_assistant` правится на своём шаге; в ядре нет ни одного предметного имени.

## ADR-51 · Факт-результат задачи: объявляет форма задачи, проверяет ядро

- **Дата:** 2026-09 · **Статус:** принято; реализует ADR-15 п.4–5 (FR-FACT-7/8)
- **Контекст:** у генеративных сервисов результат — это состояние, которое дальше живёт и растёт: сказка Taleweaver продолжается сегментами, каждое продолжение опирается на предыдущее. По ADR-15 источником новой задачи может быть только факт, в том числе факт-результат прежней задачи. Нужен механизм превращения результата в факт.
- **Решение:**
  1. Форма задачи в манифесте объявляет `result`: `fact_kind` — факт-форма результата; `versions_field` — необязательное поле-`fact_ref` задачи: результат становится **новой версией** этого факта (продолжение сказки), без него — новым фактом `origin=task:<id>`; `publish` — `draft` (по умолчанию, ADR-15 п.5) или `auto`.
  2. `publish: auto` — пользователь, отправляя задачу, уже согласился с её результатом: версия сразу `published`, прежняя опубликованная — `archived`. Для пошаговых сценариев (сказка) это снимает лишний шаг «опубликовать» между сегментами. `draft` остаётся правилом по умолчанию.
  3. Ядро никому не верит (ADR-24): результат проверяется по форме факта теми же правилами, что ввод пользователя; не прошёл → `REPORT_INVALID`, резерв снимается.
  4. Устаревшая база: если версионируемый факт получил новую версию после того, как задача взяла снимок, фиксация отклоняется (`REPORT_INVALID`, «stale base version») — два продолжения одной сказки не перетирают друг друга. Клиенту рекомендуется ставить такие задачи в одну группу (ADR-36, `group_id` = id факта).
  5. Ссылка на созданную версию — в `report.result_fact` (`fact_id`, `version`, `status`); событие `fact.changed` — той же транзакцией.
- **Последствия:** миграция `0002` (`forms.result_spec`); схема манифеста дополнена полем `result` у формы.

## ADR-52 · Токены прорабов из конфигурации

- **Дата:** 2026-09 · **Статус:** принято; дополняет ADR-18
- **Контекст:** воркеру нужен service-токен на старте; выпуск командой `issue-token` после запуска ядра не даёт поднять систему одной командой (`make up`).
- **Решение:** оператор может задать токены в `CORE_PRORAB_TOKENS` (`service:name:token`, через запятую; токен ≥ 32 символов — `openssl rand -hex 32`). При старте ядро после регистрации модулей создаёт или обновляет эти учётки; в БД — только хэш. Тот же токен передаётся воркеру его переменной окружения. `issue-token` остаётся для ручного выпуска.
- **Последствия:** токены — секреты окружения (`.env`, в Git не попадают); отзыв — удалить из конфига и отозвать учётку (админ-инструмент — следующий уровень).


## ADR-53 · Код DATA_REJECTED: воркер отверг данные

- **Дата:** 2026-09 · **Статус:** принято; дополняет реестр 5.10 (ADR-24, ADR-48)
- **Контекст:** ядро проверяет только форму данных, смысл — у воркера (ADR-49). Когда данные корректны по форме, но неприменимы по смыслу (направленный граф для коммивояжера, продолжение завершённой сказки), воркеру оставалось только `WORKER_ERROR` — класс «исполнение», и пользователю предлагался бесполезный retry.
- **Решение:** новый код реестра `DATA_REJECTED`: этап — исполнение (отчёт воркера), лечит — пользователь, класс — данные (retry нет), сообщение — «исполнитель не может обработать эти данные — исправьте и отправьте заново». В контракте шлюза у commit появляется `outcome: rejected`; причина — в `admin_message`, пользователю идёт шаблон реестра (ADR-24). Резерв снимается целиком, как у любого failed.
- **Граница:** `rejected` — только про данные бланка. Сбои провайдеров, таймауты, ошибки кода — по-прежнему `error` → `WORKER_ERROR`, retry есть.
- **Последствия:** SDK — исключение `DataRejected`; воркеры алгоритмов и Taleweaver переводят нарушения предусловий в `DataRejected`.


## ADR-54 · Фронт — React + Vite SPA за nginx вместо Next.js

- **Дата:** 2026-09 · **Статус:** принято; заменяет ADR-09 в части фреймворка
- **Контекст:** ADR-09 выбрал Next.js App Router. Но после ADR-43 весь сервер — Go-ядро, фронт не знает ни одной предметной формы (ADR-49) и строит экраны только по `meta_ui` бланка, данные у пользователя уже в IndexedDB. Серверный рендеринг ничего не даёт: без авторизации показывать нечего, SEO не нужно. Node-сервер в рантайме — лишний процесс под нагрузкой 10 000 пользователей (ADR-50).
- **Решение:** React 19 + TypeScript + Vite, статическая сборка. Раздаёт nginx, он же проксирует `/api/` и WebSocket `/api/v1/ws` на ядро: один origin, без CORS. Маршруты — hash-роутинг. Состояние — IndexedDB (отдельная база на пользователя), черновики форм — там же (ADR-42). Service worker кэширует только оболочку, ответы API не кэширует. Стили — свой CSS на токенах, без Tailwind: компонентов мало, a11y и тёмная тема проще руками.
- **Последствия:** рантайм фронта — nginx со статикой, масштабируется как CDN. Unit-тесты — vitest + jsdom, e2e — Playwright в Docker против всего стека. Ключи идемпотентности генерируются без `crypto.randomUUID` (его нет на http вне localhost).


## ADR-55 · Нагрузка: как меряем 10 000 пользователей и что поменяли в ядре

- **Дата:** 2026-09 · **Статус:** принято; уточняет ADR-50
- **Контекст:** ADR-50 обещал нагрузочный тест с критериями приёмки. Первые прогоны показали:
  - волна входов без ограничения съела бы память: argon2id берёт 64 МиБ на хэш;
  - просмотр кошелька был скрытой записью: `SELECT … FOR UPDATE` пишет в WAL и ждёт денежных операций;
  - список задач читал снимок фактов (`materialized`, сотни килобайт на задачу), хотя он нужен только воркеру;
  - nginx по умолчанию держит 1024 соединения на воркер и один раз резолвит адрес ядра.
- **Решение:**
  - одновременных argon2id на инстанс — не больше `CORE_AUTH_HASH_CONCURRENCY` (по умолчанию число CPU); остальные входы ждут слот, пока жив запрос;
  - `GET /wallets` — чистое чтение; кошелёк создаётся транзакцией, только если его ещё нет;
  - списки задач не читают `materialized`;
  - каталог кэшируется в инстансе на `CORE_CATALOG_TTL` (5 с), регистрация модуля сбрасывает кэш;
  - очереди и кошельки: частый autovacuum (миграция `0003`);
  - экосистема: `GOGC=400` + `GOMEMLIMIT`, пинг сокетов раз в 30 с. По профилю argon2id выделяет 64 МиБ на хэш и подстёгивает сборщик мусора; A/B на 200 запросах/с — p95 чтения 944 → 460 мс;
  - профилировщик Go по `CORE_PPROF_ADDR` (выключен по умолчанию, наружу не публикуется);
  - nginx фронта: `worker_connections 16384`, upstream ядра с `resolve` и keepalive — реплики подхватываются без перезапуска, сокеты расходятся по всем;
  - Postgres экосистемы: `commit_delay` (групповой fsync WAL, надёжность та же), `pg_stat_statements`;
  - воркеры на одной машине с ядром ограничены по CPU, временные файлы Taleweaver — в tmpfs.
- **Методика:**
  - 10 000 пользователей регистрируются настоящим API;
  - у каждого пользователя свой сокет: их держит `loadtool` на Go, горутина на сокет. VU k6 — это JS-рантайм в мегабайты, 10 000 штук не помещаются рядом с системой;
  - HTTP-смесь по интенсивности даёт k6: действие раз в 30 с на пользователя, ~330 запросов/с, пик ×3, платные и бесплатные задачи, входы;
  - доставка событий меряется пробой: депозит через HTTP, затем `wallet.changed` на сокете этого пользователя;
  - после прогона очередь должна опустеть, и выполняются SQL-инварианты денег.
- **Критерии приёмки:**
  - сокеты: подключено ≥ 99,9 %; 0 обрывов, 0 разрывов `seq` и 0 потерянных проб; доставка p95 < 1 с;
  - HTTP: ошибок < 0,5 %; p95 чтения < 300 мс, записи < 500 мс, входа < 2 с;
  - инварианты денег — без нарушений.
- **Последствия:** результаты и разбор узких мест — `docs/reports/load-test.md`. Цифры зависят от железа, поэтому в отчёте указаны машина и её ограничения.
- **Итог на стенде** (ноутбучный CPU на 4 потока, всё на одной машине):
  - 10 000 сокетов и корректность — выполнено: 0 ошибок, 0 обрывов, 0 разрывов `seq`, инварианты сходятся;
  - задержки выполнены до ~50 запросов/с; на проектных 330/с — нет, нужен многомашинный стенд.
- **Модель входов:** 1 вход/с — среднее для 10 000 пользователей; 5/с — пиковый сценарий.



## ADR-56 · Имя Go-модуля — `offgrid/core`

- **Дата:** 2026-09 · **Статус:** принято
- **Контекст:** путь модуля был `github.com/vlad78831457/r-aaa-core-a` — временный рабочий репозиторий. Постоянный хостинг ещё не выбран.
- **Решение:** модуль называется `offgrid/core`. Для сборки путь модуля — только имя: импорты с этим префиксом Go берёт из локальных папок проекта, а не из сети. Переезд или удаление репозитория код не затрагивает.
- **Последствия:** модуль нельзя подключить через `go get` — это и не нужно: ядро — самостоятельная программа, модули подключаются по HTTP через Python SDK. Если ядро понадобится как Go-библиотека, имя меняется на домен постоянного хостинга одной командой `go mod edit -module` и заменой импортов.


## ADR-57 · Оплата промокодами: служба оплаты отдельно от приложения

- **Дата:** 2026-09 · **Статус:** принято; развивает ADR-26 (контракт депозита) и ADR-31 (промокод)
- **Контекст:** владелец хочет отделить оплату от приложения: разные формы оформления (ИП, ООО, самозанятый) и юрисдикции, провайдеры меняются. Приложению не нужно знать ни банк, ни кассу.
- **Решение:**
  - деньги принимает служба оплаты — эмитент промокодов со своим токеном (`CORE_PROMO_ISSUERS` или `core promo-issuer`); эмитентов может быть несколько;
  - промокод — случайные 16 символов без похожих букв (80 бит); ядро хранит только sha256, сумму, валюту, эмитента, номер заказа, необязательные email получателя и срок;
  - погашение — депозит провайдера `promo:<эмитент>` по контракту ADR-26: ровно один раз (строка кода под `FOR UPDATE`, `dedup_key promo:<id>`); повтор того же пользователя — `already_redeemed`, без второго зачисления;
  - два пути: пользователь вводит код (`POST /api/v1/promo-codes/redeem`) или эмитент сообщает «оплачено, зачислите email» (`POST /issuer/v1/redeem`);
  - эмитент видит, отзывает и гасит только свои коды; повтор выпуска с тем же `external_id` не создаёт второй код;
  - подбор ограничен: `CORE_PROMO_MAX_FAILURES` неверных кодов за `CORE_PROMO_FAILURE_WINDOW` (10 за 15 минут);
  - оператор выпускает подарочные коды командой `core promo-codes` (без службы оплаты).
- **Последствия:** контракт эмитента — `contracts/interfaces/promo_issuer.openapi.yaml`, объяснение — `docs/PROMO.md`. Демо-пополнение остаётся для разработки (`CORE_DEMO_DEPOSIT`). Возврат денег после погашения (списание GC) — отдельная операция, пока нет.

## ADR-58 · Вход через внешние аккаунты: много провайдеров, Google и VK ID первыми

- **Дата:** 2026-09 · **Статус:** принято; развивает ADR-44 (своя авторизация) и ADR-25/32 (OAuth адаптером)
- **Контекст:** владелец хочет вход через основные аккаунты (Google, Apple, VK и другие), с расчётом, что провайдеров будет много; начать с Google и VK ID.
- **Решение:**
  - провайдер — адаптер с интерфейсом `oauth.Provider` (`internal/core/auth/oauth`): любой OpenID Connect подключается настройкой (`CORE_OAUTH_PROVIDERS`), провайдеры со своим протоколом (VK ID; позже Apple) — своим адаптером; Google и VK ID включаются одними ключами; провайдер без client id выключен;
  - поток — Authorization Code + PKCE (S256) + одноразовый state (в БД только хэш, 10 минут); для OIDC — nonce и проверка id_token: подпись по JWKS, издатель, аудитория, срок;
  - внешний аккаунт (провайдер + неизменный id у него) — запись `user_identities`; к существующему пользователю по email привязывается, только если провайдеру доверяем (`trust_email`) и он подтвердил email; иначе новый пользователь (email записывается, только если подтверждён доверенным провайдером); одновременные первые входы — под advisory-локом;
  - пароль и email у пользователя теперь необязательны; вход по паролю для пользователя без пароля невозможен (с тем же временем ответа);
  - сессия после возврата — через одноразовый код входа (2 минуты) в `#fragment`, фронт меняет его на токены: токены не попадают в адрес, историю и логи прокси; `return_to` — только путь своего сайта.
- **Последствия:** инструкция и регистрация приложений у провайдеров — `docs/OAUTH.md`. Для тестов и стенда — поддельный провайдер `oauthmock` (OIDC и VK ID). Связать несколько внешних аккаунтов в одного пользователя — в личном кабинете (`task/ak-cabinet`). Apple — отдельный адаптер (секрет клиента — JWT, возврат POST-ом).

## ADR-59 · Кабинет: несколько входов у одного пользователя, карточки фактов, выключаемое демо

- **Дата:** 2026-09 · **Статус:** принято; развивает ADR-58
- **Контекст:** кабинет пользователя — мои сказки и герои, баланс с историей, профиль; вход через VK создаёт пользователя без email, и ему нужен путь к Google и паролю.
- **Решение:**
  - привязка входа начинается из кабинета запросом с токеном (`POST /api/v1/me/identities/{id}/link`) — state запоминает пользователя (`oauth_states.link_user`), колбэк привязывает внешний аккаунт к нему, а не входит; аккаунт другого пользователя не перепривязывается (`taken`); подтверждённый email доверенного провайдера достаётся пользователю без email, если адрес свободен;
  - последний способ входа (нет пароля с email и нет других внешних аккаунтов) не отвязывается; пароль задаётся только при наличии email, смена — с текущим паролем;
  - список фактов отдаёт карточки: статус последней версии, время создания и выбранные поля опубликованной версии (`?fields=title,language`), `?live=true` — без удалённых; тела версий в список не попадают, ядро по-прежнему не знает предметной области (поля называет клиент);
  - журнал кошелька показывает источник пополнения (`source`: demo, promo:<эмитент>) и бланк задачи (`form_id`);
  - `GET /api/v1/features` говорит фронту, что включено (`demo_deposit`): в продакшне кнопка демо-пополнения не показывается.
- **Последствия:** экран сказки получил раздел «Кабинет»; фронт по бланкам (`/schema/`) пока без него.

## ADR-60 · Файлы пользователей: фото героев, закрытое хранилище, подписанные ссылки, доступ воркера по задаче

- **Дата:** 2026-09 · **Статус:** принято; реализует ADR-16 (реестр файлов) для картинок
- **Контекст:** к герою сказки прикладывают фото — чаще всего ребёнка — как образец внешности для иллюстраций (так было в прототипе). Нужны загрузка, хранение, показ владельцу и передача воркеру без публичных адресов.
- **Решение:**
  - ядро принимает только картинки (JPEG, PNG, WebP до `CORE_FILE_MAX_BYTES`) и пересохраняет их: поворот по EXIF, до `CORE_IMAGE_MAX_SIDE` по большей стороне, JPEG без метаданных; оригинал не хранится; размер полотна проверяется до распаковки, одновременных пересохранений — не больше половины CPU;
  - байты — в хранилище за интерфейсом `files.Store` (сейчас каталог на общем томе реплик, в облаке — закрытый S3-бакет), учёт — в реестре `files`; квота живых файлов на пользователя;
  - владелец видит файл по подписанной ссылке (HMAC от секрета ядра, срок `CORE_FILE_LINK_TTL`) — `<img>` работает без токена; чужой или неверно подписанный запрос неотличим от отсутствующего файла (404);
  - снимок задачи раскрывает файлы и внутри фактов, на которые ссылается бланк (фото персонажа); прораб скачивает байты `GET /gateway/v1/tasks/{id}/files/{file_id}` — только пока задача у него в работе и только файлы из её снимка;
  - `allowed_file_types` поля проверяется при создании факта и задачи;
  - удаление файла стирает байты; ссылки на него в фактах и снимках становятся `LOST_REF`;
  - воркер Taleweaver отдаёт фото моделям картинок, которые принимают образцы, и не сохраняет их; выключатель — `HERO_PHOTOS=off`.
- **Последствия:** объяснение для владельца и вопросы о согласии на передачу фото — `docs/PHOTOS.md`. Резервное копирование должно включать том `files`. Голос героя (аудиофайлы) — тем же путём, когда воркер научится им пользоваться.
